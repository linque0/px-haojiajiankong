# 00 大方向与产品形态 —— 项目总定位

> 版本 v1.0（2026-10-02）。本文档是项目的最高定位文件：所有后续开发（docs/01 管线、docs/02 词表、docs/03 价值规律、看板与插件）都以此为准。

---

## 1. 最终目的（锚定，不再漂移）

**做一个用于监控游戏账号价格变化趋势、并能更好制定购买策略的监控看板/插件。**

拆开是两个目的、两类决策场景：

| 目的 | 用户问题 | 决策场景 | 决策发生的位置 | 交付载体 |
|---|---|---|---|---|
| **价格趋势监控** | "我关注的游戏/段位现在什么行情？在涨还是跌？什么时候是买方市场？" | 时间维度（何时买） | 离开网站看行情 | **趋势看板** + 趋势周报推送 |
| **购买策略** | "这个账号值不值这个价？现在该不该出手？" | 单品维度（买哪个、什么价买） | 逛网站挑号的**瞬间** | **浏览器插件（原位显示）** + 捡漏推送 |

## 2. 大方向决策：一个内核，双前端

**核心资产 = 采集管线 + 游戏词表 + 估值模型 + 事件库**（docs/01–03 已规划的全部后端），它不随前端形态变化。前端按两个决策场景分两路交付：

```
                 ┌─ 前端 A：趋势看板（Streamlit，docs/01 §7 已设计）
                 │    市场总览 / 价格指数 / 趋势阶段 / 去化 / 趋势周报
内核：管线+词表 ──┤
+估值模型+事件库 ─┼─ 前端 B：浏览器插件（pxb7 页面原位注入）
                 │    列表卡片注入 deal_score；详情页注入 预测价 vs 挂牌价 + 价格历史 + 五因子归因
                 │
                 └─ 通知层：飞书/webhook 推送（A1 捡漏 / A2 降价 / A5 趋势转折）——覆盖两个场景的中间态
```

**为什么两个前端都要**：购买决策发生在两个物理位置——研究行情时不在网站上（看板），实际挑号时在网站上（插件）。只做看板，决策瞬间缺支持；只做插件，看不到趋势与时机。

**为什么先看板后插件**：插件的价值 = 模型覆盖度 × 显示效果，模型没覆盖的游戏/属性插件就是白屏。先建模型并在看板上验证（R²、捡漏信号回测），再上插件。

**插件的技术选型决策**：阶段二用 **Tampermonkey 用户脚本**起步（开发快、免打包审核、个人使用零分发合规负担），形态成熟后视需要升级为正式 Chrome 扩展。数据流：用户脚本读取**用户正在浏览的页面**上的 listing ID → 查询本地 API（localhost，读我们自己的 DuckDB/模型缓存）→ 原位注入徽标 → **不向 pxb7 新增任何请求**。这是全项目合规姿态最优的一环：插件只加工用户自己浏览行为产生的页面。用户脚本天然运行在用户自己的登录会话内——与管线的"登录态优先"策略（docs/01 §3.1 v1.3）口径一致，插件里看到的可见数据与采集端相同。

## 3. 购买策略体系（三层输出，全部带归因）

| 层 | 形态 | 内容 | 依据模块 |
|---|---|---|---|
| **L1 信号层**（被动） | 推送 | A1 捡漏提醒（新上架 deal_score < P5）、A2 降价提醒（≥10% 或 ≥500 元） | M3/M8 + 预警引擎 |
| **L2 决策支持层**（主动） | 插件原位显示 | 预测价 vs 挂牌价、price_band、五因子归因（"值在哪/亏在哪"）、同listing价格历史 | M2/M8 + docs/02 词表 + docs/03 规律 |
| **L3 时机层**（策略） | 看板 + 周报 | 价格指数趋势与阶段（rising/peak/declining）、买方市场识别（指数下行+供给过剩）、事件日历（版本更新前抛压、赛季末、复刻/追缴事件） | M7 + fct_event |

**决策输出规范**：每条建议必须附归因明细与置信度（样本量/模型误差）；"建议"≠"保证"——挂牌价≠成交价、下架≠成交的口径披露在全前端保留；**不做自动下单、不做代购**（写死，见 §5）。

## 4. 阶段路线（大方向的落地节奏）

| 阶段 | 内容 | 验收（通过才进下一阶段） |
|---|---|---|
| **一：内核+看板**（docs/01 W1–W3） | 采集管线、词表抽取、M1–M8 指标、趋势看板、推送 | 采集成功率 ≥95%；模型披露 R²（P50 误差 ≤15%）；捡漏信号回测有效（信号 listing 7 日 delist 率显著高于同段基线） |
| **二：插件**（本方向新增，对应 docs/01 W4） | Tampermonkey 用户脚本：原神等 P0 游戏的列表页 deal_score 徽标 + 详情页预测价/历史/归因面板 + 与推送打通 | P0 游戏覆盖率 100%（命中任务的游戏卡片全部有徽标）；本地 API 响应 <100ms；零新增 pxb7 请求 |
| **三：策略回测与铺开**（W5+） | 信号回测体系化（推荐→实际成交推断胜率）、阈值校准、多游戏铺开、可选 Docker/CI | 回测报告；周报自动化 |

## 5. 边界（写死）

1. **个人工具**：本地部署、自用；插件以用户脚本形式本机加载，不发布应用商店（规避分发与平台对抗问题）。
2. **只做研究与决策支持**：不做自动下单、不做代购、不做撮合；不抓卖家个人身份信息。
3. **插件零新增请求**：只读用户自己浏览的页面 + 调本地 API；采集仍由管线按 docs/01 §3 规范执行。
4. **登录态优先采集**（v1.3）：管线默认以自有专用小号的持久化登录态运行（主备双号冗余、限速档不放松、不并发轮换），游客态仅作失效降级通道；登录态文件不入 git。
5. **口径诚实**：所有前端保留"挂牌价≠成交价、下架≠成交"披露；模型未覆盖时显示"不可估"而非编造。

- docs/02（词表）、docs/03（价值规律）：直接喂 L2 归因显示与 L3 时机层，无需改动方向。
