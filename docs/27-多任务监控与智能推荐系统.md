## 1. 目标与边界

### 1.1 目标

让系统持续积累可比较的市场观察，并让用户以「监控任务」描述关注的账号。最终自动完成：

1. **巡检**：按用户设置的时间、范围和批量驱动浏览器采集；默认采用列表基础数据、完整介绍及必要详情回退的混合路线（复用扩展既有能力，见§26）；
2. **入库**：沿用现有解析 / 词表 / 快照管线（不做第二套入库逻辑）；
3. **判定**：对新入库账号做结构化条件判定，筛出候选（预算、必选角色/武器/链位、资源下限、区服、风险词排除）；
4. **分析**：分别计算同账号价格变化、同配置挂牌趋势、研究估值与可靠性；推荐理由先由结构化证据生成，LLM为可选解释层；
5. **浏览**：在采集看板查看任务与数据健康，在价值看板查看价格观察、估值和候选理由。

先完成性能基线、本地处理优化、全文快速路径和大批验证，再接入稳定调度、价格复采与可复核候选，按§23阶段消费既有估值产物和成对价格分析。满足心仪条件、价格较低、估值偏离是三种不同信号，不合并成未经验证的“性价比分”。实施顺序见§26.8。

### 1.2 本期边界（不做清单）

- 不实现推送**发送**（渠道扩展、消息外发）；只保留字段、冷却台账与发送函数接口（§13）。
- 不做条件表单化编辑 UI（P0 在 `config/tasks.yaml` 编辑；P1 再做表单）。
- 首个闭环必须支持有限额的新账号详情补齐；有详情条件的候选不能仅凭列表通过。无需先做通用开关UI，按任务所需字段决定补齐队列（§18、§21）。
- 本期采集完整账号介绍和公开文字字段，不下载、保存或识别图片内容；明确未公示与采集失败分别记录，完整性范围见§26.6。
- 不接入估值模型偏差评分（P1 以只读文件契约接 `data/analysis/valuation/wuwa-v2` 发布产物）。
- 周期性挂牌趋势报告纳入后续路线（§20、§23）；首期不训练未来涨跌预测、不设主观资产人民币固定权重，不自动下单 / 代购 / 撮合。

## 2. 对标分析与取舍（ai-goofish-monitor）

参考项目核心结构：FastAPI + Vue3 + SQLite + APScheduler + Playwright；任务 = 关键词/价格/筛选/AI 判定标准/cron；每个商品送多模态 LLM 判定 `is_recommended`；7 渠道推送；结果页与任务日志。照搬与本项目冲突，取舍如下：

| 参考项目做法 | 本方案 | 理由 |
|---|---|---|
| Playwright 服务端直连采集 | **替换**：扩展后台标签页巡检 | pxb7 WAF 按自动化环境特征拦截（docs/01 v1.4 实测）；红线禁止指纹伪造（docs/01 §3.2） |
| APScheduler + 每任务一个子进程 | **替换**：网关进程内轻量调度线程 | 复用常驻网关与风控状态机；零新依赖；天然串行（符合"同一登录态不并发"纪律） |
| SQLite + FastAPI + Vue 管理后台 | **替换**：8870统一管理入口复用既有8765采集工作台与价值分析前台 | 不重建管理前台；职责见§22，已交付的界面合并见§25 |
| 多模态 LLM 全量判定每个商品 | **替换**：规则筛选在前、LLM 只写候选理由 | 已确认决策；docs/01 §1 已论证「结构化属性 + 统计模型」对螃蟹优于 LLM 且零 token 成本 |
| 7 渠道推送（ntfy/Bark/企微/Telegram 等） | **保留设计，暂不实现发送** | 已确认决策；只落接入点与冷却台账（§13） |
| 已见去重、任务级结果浏览、失败熔断 | **采纳** | 对应现有 listing 去重、`monitor_job` 台账、风险状态机与扩展「连续 3 次失败暂停」 |
| 代理池 / 账号轮换 / 指纹规避 / 自动下单 | **不采纳** | 红线（docs/01 §3.2、docs/00 §5） |

## 4. 硬约束（设计必须服从）

1. **采集通道**：使用真实浏览器扩展；按2026-10-13用户授权，可研究减少验证触发及自动完成普通滑块。v0.5.14按配置尝试一次浏览器输入并核验解除后续采，详见docs/13；不做指纹伪造/外部打码/协议逆向/代理池。传统Playwright通道尚未恢复（docs/01 §3.2、docs/10 §4）。
2. **限速与退避需分通道核对**：既有CLI档位包括单页3–6s、任务间隔≥60s、每任务每轮≤5页、每日2–4轮及验证码24h/空响应6h退避。2026-10-12实验中的扩展配置为详情200ms、标题3000ms与扩页2s，不能声称CLI闸门已自动覆盖插件，也不能当作网站允许阈值。未来调度适配需显式接线和测试；可依据性能与失败证据重新评估节奏，不以取消验证暂停或无界重试提效。本次仅文档，当前手动配置保持原值；验证等待与后续调度退避分别处理，见§19、§26.10。
3. **「实时」的真实含义**：= 加密轮次 + 缩小页数 + 小额预算，不是无间隔轮询；实际粒度受浏览器在线状态与 MV3 `chrome.alarms` 最小周期（现状按 1 分钟，保守取值）约束。
4. **浏览器需保持开启**（后台标签页即可）；关闭期间任务保持待领取、超期作废，不积压（§7.4）。
5. **判定口径**：0 ≠ 缺失（零余额是有效数据，docs/25 §8.6）；样本不足不发结论（`min_cell_sample=30`）；挂牌价 ≠ 成交价；不填 0、不伪装成功（docs/10 §5）。
6. **LLM 纪律**：仅对规则筛出的候选调用；凭据只从环境变量读取、仓库无字面量；出网请求过 `urlguard`（仅 http/https、拒绝内网/回环/保留地址、禁重定向，与 `notify.py` 同纪律）；未配置/失败时降级模板理由。送 LLM 内容仅为挂牌属性与价格，不含卖家信息、不含原始 DOM（docs/00 §5-2）。
7. **入库唯一性**：巡检入库复用现有 `_ingest_cards` 路径与轮次幂等（`write_snapshot_round(scope="batch")`）；不新开旁路写入。

## 5. 任务模型

### 5.1 `dim_task` 扩展列

`ADD COLUMN` 幂等迁移，旧任务默认 `manual`，完全兼容现状：

| 列 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `monitor_mode` | VARCHAR | `manual` | `manual`=（现状）仅手动/被动；`scheduled`=按每日轮次；`realtime`=固定小间隔 |
| `interval_minutes` | INTEGER | NULL | realtime 轮次间隔基准（下限见 §5.3） |
| `active_hours` | VARCHAR | NULL | 生效时段如 `09:00-23:00`；NULL = 全天 |
| `daily_page_budget` | INTEGER | NULL | 每日页预算（本任务当天最多加载的列表页数） |
| `max_sweeps_per_hour` | INTEGER | NULL | 每小时最多巡检轮次 |
| `new_accounts_target` | INTEGER | NULL | discover的用户设置新增目标N；未设置时继承当前手动cards_target，不新设默认10；较大逻辑任务按现有协议拆执行块 |
| `batch_size` | INTEGER | NULL | price_refresh/detail_enrich的用户设置处理数量N；未设置时继承当前手动采集数量，ID清单和处理数量分别保存 |
| `purpose` | VARCHAR | `discover` | `discover` / `price_refresh` / `detail_enrich`，执行与停止条件见§18 |
| `watch_json` | VARCHAR | NULL | 判定条件（§8.1 schema） |
| `notify_json` | VARCHAR | NULL | 推送预留（§13；本期只存不发） |

`config.py::Task` 同步扩展 + 校验；`dim_task` 随 `init_db(refresh_tasks=True)` 同步（现机制不变）。

### 5.2 配置来源与启停

- **定义来源（人写）**：`config/tasks.yaml`（保持唯一任务定义源，注释即文档）。
- **启停与运行覆写（机器写）**：新增 `data/state/monitor_overrides.json`（同 `paths_override.json` 先例）：`{task_id: {"enabled": false}}`。调度器合并读取：`tasks.yaml.enabled` 与覆写文件同时生效（覆写优先）；看板开关写此文件，不改 `tasks.yaml` 注释与结构。
- 任务变更生效：网关启动时读取；新增 `POST /monitor/reload` 触发重新加载 tasks.yaml + `init_db(refresh_tasks=True)`（P0 由看板按钮或 CLI 调用）。
- 数量取值：任务单独设置优先，未设置时继承当前手动采集配置；开始执行时将最终取值冻结到job参数，运行中修改只影响下一批。批量、访问预算和执行时刻分别配置（§26.2）。

### 5.3 校验规则（`config.py`）

| 项 | 规则 | 级别 |
|---|---|---|
| `interval_minutes` | realtime 时必填且 ≥5 | 错误 |
| `daily_page_budget` | 1–200 | 错误（超 120 警告） |
| `max_sweeps_per_hour` | 1–12 | 错误 |
| `active_hours` | `HH:MM-HH:MM`，起 < 止（不支持跨天，跨天拆两条任务） | 错误 |
| `new_accounts_target` / `batch_size` | 未设置则继承手动值；显式值为正整数，按purpose使用；现有1–200等边界作为执行块兼容约束，不静默截断逻辑总目标 | 错误（无效值）；较大任务拆块 |
| `watch_json` | §8.1 schema 校验（未知条件类型报错，不静默忽略） | 错误 |
| `monitor_mode != manual` 且 `enabled` | 允许（但调度器仍受风控闸门与预算约束） | — |

## 6. 巡检执行链路（扩展端）

### 6.1 时序

1. 调度器 tick（30s）为到期任务写入 `monitor_job(status=pending)`（§7）。
2. 扩展 SW 每分钟 alarm 轮询 `POST /monitor/job/claim`（与既有 `/backfill/job/claim` 同通道；正采集时跳过）。
3. 领取成功（网关改claimed与可续租租约10分钟）→ SW建后台工作标签页，按purpose导航已核验列表或已保存商品链接。可批量取得的价格/文字优先从列表读取，明确ID的缺项再逐项回退，不默认将所有复采账号直接送入详情；URL参数可行性见§15-1。
4. SW 与内容脚本按`detail-context`式握手确认`job_id/task_id/purpose`与对应额度；握手前禁止普通自动采集抢跑，避免一页启动两项任务。
5. discover复用sweep.js按本批冻结的新增目标N扩页，受扫描预算约束；price_refresh/detail_enrich按用户处理规模执行明确ID清单。较大任务拆执行块并承接检查位置、去重与累计进度，子块不重置本轮/每日预算。
6. 自动选择模式按“列表基础数据 → 完整介绍 → 字段核验 → 必要详情回退”执行；用户仍可指定详情模式。网关校验有效job归属并复用原管线入库（§6.3），缺项进入待补齐，补齐后再评价（§21、§26.4）。
7. 内容脚本复用现有`collection-begin`/`collection-progress`消息和详情队列回报；monitor作为工作来源、purpose作为任务目的，不直接把既有采集mode改成未经适配的monitor值。finish以完整链路终态回报new / refreshed / details / incomplete / error。
8. 网关记录done/partial/failed与结果摘要并关闭工作标签页；批次结束触发按游戏合并导出和一次增量分析，入库、导出与分析状态分别显示。导出/分析失败不重新访问站点（§26.5、§26.7）。
9. 验证码中断：工作标签页前置并复用既有暂停/恢复（`waiting_verification`，用户完成后自动续采）。
10. 连续失败：复用扩展「连续 3 次失败暂停」；对应 job 记 `failed`，风险信号交 `detect_signals` 评估退避。

### 6.2 与既有机制的关系（全部复用，不新造）

| 机制 | 复用方式 | 差异 |
|---|---|---|
| backfill job claim | 端点多一个 `/monitor/job/claim`，SW 同时轮询两者 | 补录任务仍在网关内存单槽（现状保留）；巡检走 DB 队列（多任务 + 历史） |
| 详情队列 | 复用单工作标签页、串行和有界重试 | 新增字段依赖驱动的补齐与旧ID价格刷新来源；不另建并发详情采集器 |
| 验证暂停/恢复 | 原样复用（`verificationPause` / `verificationResume`） | — |
| 连续失败暂停 | 原样复用（3 连败 → paused） | — |
| 自更新 alarm | 不动 | 巡检运行时自更新已由 `checkSelfUpdate` 的 running 判断保护 |

### 6.3 入库归属与 targets 关系

- 巡检ingest由有效`job_id`查得任务归属，核对领取代次、任务启用、游戏/商品类型/页面来源、采集范围及本轮预算；不能仅凭客户端自报`task_id`跳过targets。任务目标与被动采集targets可不同，但必须由已启用任务定义授权；无有效job的被动路径保留现有targets校验。
- 同一 game 多个任务：以显式 `task_id` 区分；被动采集仍按 `match_task` 首个匹配（现状语义，本文披露其局限）。
- `delist` 推断：巡检为分片覆盖，沿用网关现状（**不推断下架**，`infer_delist=False`），避免把未覆盖分片误判下架（docs/01 §4 口径）。

## 7. 调度器（`pxb7/monitor.py`）

### 7.1 到期计算

- **realtime**：`next_due = last_finished + interval_minutes`，再与「预算配速」取大：`budget_pacing = 剩余生效时长 / 剩余页预算 × 单轮页数`；超预算则当日不再排。
- **scheduled**：支持用户设置每日时刻，§18的10:00/20:00仅为试点示例；未配置时刻的旧方案按runs_per_day均匀铺进active_hours，可选有界抖动。到期、领取、执行时间分别记录，不将在线或预算延迟误称准点执行。
- 统一在 tick 内计算，`next_due` 可观测（看板显示）。

### 7.2 闸门链（依次，任一不过即跳过本轮）

1. `RiskMachine.check_before_run(task_id)`（含全局停采、退避、试探档）；
2. 全局任务间隔 ≥60s（`RiskState.last_task_finished_at`）；
3. 本任务当日页预算未用尽、当小时轮次未超 `max_sweeps_per_hour`；
4. 全局无claimed/running/waiting_verification的执行任务（含手动/补录队列）；每个逻辑任务最多一条未决job，pending可按不同任务有界排队；
5. 浏览器心跳在线（§7.4）。

### 7.3 队列写入与租约

- 写入`monitor_job`：`job_id = task_id + 轮次时间戳`；保存purpose、已核验URL、参数和额度。discover为new_accounts_target，refresh/enrich为明确ID清单；旧cards_target仅在兼容层映射（§18）。
- claim时置claimed与10分钟可续租的执行租约；running阶段由进度心跳续租。waiting_verification单独持久化、保留标签页和当前项，不由10分钟普通租约计时误过期（§19）。
- 租约超时未 finish → 由调度器标 `expired`（并写事件），下一轮到点重新排；**不自动重派**（避免未知副作用下重复采集）。

### 7.4 浏览器心跳

- 任何来自扩展 origin（`chrome-extension://…`）的请求都会刷新网关内存 `last_extension_seen`；SW 的每分钟 claim 轮询是主要心跳源。
- `now - last_extension_seen > 3min` → 视为离线：不排新 job；看板显示「等待浏览器」；离线超过 30 分钟写一条运维事件（P1 起可接 A4 推送）。

### 7.5 CLI 与测试钩子

`run.py monitor status | run-once [--task id] | enqueue --task id | evaluate --task id [--all]`
（`run-once` 立即执行一轮 tick，用于离线测试与手动补跑；`evaluate` 见 §8.3。）

### 7.6 伪代码

```
每 30s tick:
  for task in tasks(enabled, mode != manual):
      if not in_active_hours(task): continue
      if not due(task): continue
      if not gates_pass(task): continue
      enqueue_monitor_job(task)      # 每任务至多1条未决；领取与执行全局单飞
  expire_stale_jobs()
```

## 8. 判定引擎（`pxb7/watch.py`）

### 8.1 条件 schema（`watch_json`）

```jsonc
{
  "budget": {"price_min": 300, "price_max": 8000},
  "require": [
    {"field": "five_star_chars", "min": 6},             // 快照列数值比较（含边界）
    {"field": "server", "equals": "官服"},               // 枚举等值
    {"chain": {"name": "爱弥斯", "min": 3}},             // 具名链位（features.five_star_character_chains）
    {"weapon": {"name": "千古洑流", "refine_min": 1}},    // 具名精炼（features.five_star_weapon_refinements）
    {"resource": {"lunite_cnt": 160}},                   // 资源下限（0 是有效值）
    {"feature": {"key": "constellation_cnt", "min": 3}}, // features 数值通用比较
    {"keyword": {"keyword_id": "…", "hit": true}},       // 词表命中（fct_listing_keyword）
    {"exploration_remaining": {"min": 5000}}             // 地图预计剩余星声；未采到=unknown待补齐
  ],
  "exclude_keyword_type": ["risk"]                       // 命中即排除
}
```

**可用字段（白名单，未列出的键配置时报错）**：

- **快照列**：`price_yuan`、`level`、`yellow_cnt`、`five_star_chars`、`five_star_weapons`、`primogems`、`intertwined_fate`、`artifacts`、`skins`、`favorites_cnt`、`viewers_masked`、`server`（枚举）、`official_verified` / `has_compensation`（布尔）。
- **features 键（按游戏词表画像）**：鸣潮资源五件套 `astrite_cnt 星声 / lunite_cnt 月相 / afterglow_coral_cnt 余波珊瑚 / lustrous_tide_cnt 浮金波纹 / radiant_tide_cnt 铸潮波纹`；`constellation_cnt`（最高链）；`five_star_weapon_refined`（最高精炼）；`five_star_character_chains` / `five_star_weapon_refinements`（具名清单，供 `chain` / `weapon` 条件）；`wuwa_map_exploration`（地图探索，`exploration_remaining` 取其余额估计）；付费商品 `vehicle_frame_modules / motorcycle_ornaments / character_skins`（清单，可选存在性）。
- **词表**：`fct_listing_keyword` 命中（按 `keyword_id` 或 `keyword_type`），类型沿用 ceiling / floor / risk / resource / segment。

### 8.2 求值口径

1. **0 ≠ 缺失**：资源类0参与比较；未知（NULL/未采到）暂不通过推荐并记录缺项，进入待补齐或明确unknown，不能当0或永久条件不匹配。已知数值不满足条件才记rule_failed（§21）。
2. **样本门槛**：价格带信息来自 `v_price_band`，`domain_n < min_cell_sample(30)` 时该维度显示 `unpublished`，不影响规则命中，仅不出带位结论。
3. **风险词排除**：`exclude_keyword_type` 命中即淘汰（记录在推荐行 `excluded_reason`，可追溯）。
4. **模板理由**：由命中条件与带位拼装（如"价格 ¥X 位于鸣潮分域 floor/low 带；五星角色 N 个；爱弥斯 3 链；月相 160"），不生成任何未提供的数字。

### 8.3 触发与存量评估

- **增量触发**：列表/详情成功入库后异步安排归属任务评价，覆盖new/changed/refreshed及必要字段补齐；命中或资格变化幂等更新recommendation。分析/LLM失败不回滚已成功入库的价格事实（§21—§22）。
- **存量批评估**：计划CLI对指定游戏/区服的最新数据求值（本轮鸣潮1991商品），输入只读，推荐表幂等upsert；不称为“全流程只读”。旧数据按新鲜度标记历史候选，未复核价格不能作为当前推荐。

### 8.4 推荐记录与去重

- 同 listing 同任务只保留一行，重复命中更新时间与命中快照；状态流转 `new → seen → ignored`（看板操作）。
- `alert_history`（§13）登记冷却键 `task_id:listing_id:rule`，为将来推送去抖（本期只登记不发送）。

## 9. LLM 推荐理由（`pxb7/ai.py`）

### 9.1 触发与限量

- 仅对：规则全过、`recommendation.status='new'`、`reason_llm IS NULL` 的行调用。
- 限量：`settings.llm.max_per_day`（默认 20）与单任务每日上限（默认 10）；超出跳过，模板理由照常展示。
- 未配置（`PXB7_LLM_BASE_URL` / `PXB7_LLM_API_KEY` / `PXB7_LLM_MODEL` 任一为空）→ 全量跳过，无报错。

### 9.2 输入输出契约

**输入（仅结构化字段，不含卖家信息/DOM）**：

```json
{"game": "鸣潮", "price": 2680, "band": "low", "domain_n": 412,
 "attributes": {"level": 60, "yellow_cnt": 21, "five_star_chars": 9, "five_star_weapons": 6},
 "features": {"lunite_cnt": 320, "constellation_cnt": 4,
              "five_star_character_chains": [{"name": "爱弥斯", "value": 3}]},
 "matched": [{"type": "chain", "name": "爱弥斯", "min": 3}], "server": "官服"}
```

**输出（容错解析）**：

```json
{"reason": "≤200字中文", "highlights": ["…"], "cautions": ["…"]}
```

解析：剥代码围栏、提取首个 JSON 值、容忍 `reasoning_content` 字段；失败 1 次即放弃本次（不重试轰炸）。

### 9.3 提示词与合规

- 模板内置于 `pxb7/ai.py`；若存在 `config/llm_prompt.md` 则以其覆盖（占位符 `{{payload}}`）。默认模板要点：角色 = 游戏账号交易研究助手；只允许引用输入字段；禁止编造数字/卖家信息/成交价；输出仅 JSON；口径披露（挂牌价 ≠ 成交价）。
- 请求：`urllib` + `urlguard.assert_safe_url`（禁重定向、拒绝内网/回环/保留地址）、超时 15s、`Content-Type: application/json`。
- 凭据只从环境变量读取；仓库任何文件不写可用凭据（与 `notify.py` 纪律一致，测试含明文扫描断言）。

## 10. 数据模型

### 10.1 新表（`db.ensure_monitor_schema`，幂等）

```sql
CREATE TABLE IF NOT EXISTS monitor_job (
  job_id VARCHAR PRIMARY KEY, task_id VARCHAR NOT NULL,
  status VARCHAR NOT NULL,              -- pending / claimed / running / waiting_verification / done / partial / failed / expired / cancelled
  url VARCHAR, params_json VARCHAR,
  created_at TIMESTAMP NOT NULL, claimed_at TIMESTAMP, finished_at TIMESTAMP,
  lease_expires_at TIMESTAMP, result_json VARCHAR, error VARCHAR);

CREATE TABLE IF NOT EXISTS recommendation (
  listing_id VARCHAR NOT NULL, task_id VARCHAR NOT NULL,
  snapshot_at TIMESTAMP, price_yuan DECIMAL(18,2), band VARCHAR,
  matched_json VARCHAR, excluded_reason VARCHAR,
  reason_template VARCHAR, reason_llm VARCHAR, llm_model VARCHAR, llm_at TIMESTAMP,
  status VARCHAR NOT NULL DEFAULT 'new',   -- 用户状态 new / seen / ignored；资格另存eligibility（§21）
  updated_at TIMESTAMP NOT NULL,
  PRIMARY KEY (listing_id, task_id));

CREATE TABLE IF NOT EXISTS alert_history (
  dedup_key VARCHAR PRIMARY KEY,          -- task_id:listing_id:rule
  listing_id VARCHAR, task_id VARCHAR, rule VARCHAR,
  created_at TIMESTAMP NOT NULL, sent BOOLEAN NOT NULL DEFAULT FALSE);
```

索引：`monitor_job(task_id, status)`、`recommendation(status, updated_at)`。

此SQL为v1.0骨架，不是可直接执行的最终迁移。v1.1实施需同时纳入§22.3的purpose/阶段/领取代次、recommendation资格与版本、追加式market_observation；完整字段、约束及兼容迁移在实施步骤1确定并测试。

### 10.2 迁移与备份

- `db.ensure_monitor_schema(conn)`：`dim_task` 逐列补齐（先 `PRAGMA table_info` 判存在再 `ALTER TABLE ADD COLUMN`，避免依赖具体版本的 `IF NOT EXISTS` 语义）+ 建表 + 建索引。
- 升级路径沿用 `collection.upgrade` 先例：`CHECKPOINT` → 有数据先备份到 `data/backups/` → 幂等执行；调用点：`init-db`、网关启动（现状仅 `_apply_config_paths` 调 `init_db`，需新增启动迁移调用）、`monitor` CLI。

### 10.3 视图

`v_recommendation`以`(listing_id, task_id)`为一行，按ID连接`v_listing_analysis`与`dim_game`展示。现有分析视图提供最新快照；推荐证据另按其snapshot_at/研究批次读取，最新价或资料与证据版本不一致时标待重评，不拼成一条“当前有效”推荐。条件求值在watch.py，视图只连接展示；测试连接前后粒度一致。

### 14.2 端到端手测清单（真实浏览器）

## 18. 数据积累：新发现、价格复采、详情补齐三条任务

### 18.1 分开目标、停止条件与预算

| purpose | 核心目的 | 一批额度与停止条件 | 对重复账号的处理 |
|---|---|---|---|
| `discover` | 发现新挂牌、扩充配置覆盖 | 用户设置本批新增目标N；达到N或扫描预算/列表终点即停止 | 仍按ID去重，不清空去重；遇到已到期的旧账号可顺带登记价格观察 |
| `price_refresh` | 跟踪已有账号价格、状态和资产变动 | 用户设置本批处理数量N、监控范围或选定ID；完成指定观察或预算耗尽停止 | 即使没有新账号也正常完成；价格不变也登记“本次确实观察到” |
| `detail_enrich` | 补齐估值/条件所需字段、解决变化与冲突 | 用户设置本批处理数量N、缺项范围或选定ID；沿用一次有界自动补采 | 仅缺项/冲突/资产变化需要补齐；已确认0或明确未公示不反复采 |

**10仅为历史自动采集试点的任务条数，不是默认值、固定批额度或系统上限。**旧扩展cards_target现在实际表示新增额度，不是扫描数量。未来discover使用用户设置的new_accounts_target，refresh/enrich使用batch_size与明确ID清单；未设置时继承当前手动配置，开始后冻结取值。cards_seen、列表加载数、refresh_target_ids、成功详情和补齐数各自记录，禁止price_refresh走“新增不足继续扩页”的逻辑。

现有扩展有200条等执行边界，较大逻辑任务拆执行块，总目标仍为用户设置值。执行块承接检查位置与去重，累计新增/更新/补齐/失败；达到终点或预算不足时披露未完成量，不重新加载同一列表凑数，也不按子块重置本轮/每日预算（§26.2）。

旧任务默认manual，现有手动采集行为保持兼容。手动采集、补录、监控共用同一扩展忙碌状态与串行执行锁；某页出现验证时，不能由另一个监控任务抢占现场或重新打开同一账号施压。

### 18.2 首个试点的配置示例（批量由用户设置）

以下频率、篮子与预算仅为未来实施的**试点设计示例**，不是已应用配置、系统固定限制或经实测确定的网站阈值；本批数量、每日预算和执行时刻分别由用户配置：

- 先以鸣潮官服试点，自动监控默认关闭；主动开启后，可选择每日10:00、20:00两轮（Asia/Shanghai），每轮按用户新增目标N执行，示例扫描预算为5次列表加载。排序与筛选需实际页面确认，不使用猜测参数；失败时记录默认综合排序及覆盖限制。
- 可选100个有效旧账号作为固定观察篮子示例，按冻结时点价档、核心配置类型分层，在层内按ID稳定抽样；保存篮子版本、权重及加入/退出原因。复采周期示例24小时，每批按用户处理数量N执行；新增候选进入独立短期清单，不偷偷替换固定篮子。
- 示例每日列表加载预算20、详情访问预算200，示例任务间隔≥60s、扩页间隔≥3s；这些数值独立于本批账号目标，部署前登记并按证据评估。发现、刷新、补齐及失败/重试共同消耗预算；详情预算计导航尝试，不只计成功。本次文档不改变当前手动设置，节奏研究见§4、§26.10。
- 调度顺序为用户已排任务优先；自动任务中先满足到期价格刷新，再补齐必要字段，最后做新发现，并按最早到期顺序轮转，防止同一任务永久饥饿。剩余预算不足时明确deferred与下一次时间，不把延后记成功。
- 显示到期时间与实测数据年龄，不承诺5—20分钟“实时”。先七天测量单批耗时、验证与人工介入、浏览器在线时间和成功率，再依据数据修订频率及篮子规模，不靠降低间隔提升吞吐。

100个固定账号仅是篮子示例，与每批处理规模无关，不能作为官服全市场指数。全区服扩展需逐个核验站点筛选与区服字段；账号、初始号、代练、充值不混入同一采集范围或估值池。

### 18.3 提效重点：只付出有用途的访问成本

列表就地读取价格和清单；稳定资产沿用有时间和原文来源的最近已核资料，只有候选依赖字段缺失、名册变化或资料过期才访问详情。列表无法找到固定旧ID时，可由现有扩展单标签页访问已保存商品链接核验，不猜站点私有接口。失败重试有界、预算不足明确延期，禁止批量并发详情。

扩大样本优先补足区服/价档/配置域的空白与稀有资产支持，同时留出一部分不经过推荐条件筛选的探索样本，避免仅采“看起来便宜”账号导致训练样本偏差。反馈和推荐结果不能直接变成成交真值。早先10详情55秒的结果不含验证等待、任务冷却和全市场覆盖，不能按比例外推每日采集能力。

## 19. 自动化运行与中断恢复闭环

### 19.1 可用级别要分别验收

| 级别 | 达成条件 | 当前状态 |
|---|---|---|
| 单批自动执行 | 启动后自动采集、入库、结束 | 已有10账号真实实验 |
| 定时运行、验证时需人 | 自动到期/领取/执行；遇验证保留任务并提示；解除后续采 | 组件部分可复用，调度与整体联动未实施 |
| 长期无人值守 | 连续七天实际到期任务执行且人工介入0，验证和故障处理同样有证据 | 尚未达成，不以单次拖动成功替代 |

当前浏览器工具对每次CAPTCHA操作要求操作当时确认。本方案不把对话中的一次确认改成永久授权，不增加绕过、验证码令牌重放或反复刷新挑战。七天实验可以先测“有人值守的定时系统”，其中任何验证码确认/手动处理都计人工介入；只有实测达到0才能标记无人值守。若验证成为瓶颈，保留队列、调整经证据支持的任务预算，并调查平台授权数据合作渠道；渠道未确认前不宣称可接入。

### 19.2 任务状态、租约与恢复

未来`monitor_job`状态采用`pending → claimed → running → done/partial/failed`，另有`waiting_verification`、`expired`、`cancelled`。任务阶段与终态分开，保存当前ID、已成功ID、原快照轮次、预算消耗、来源标签页与领取代次；列表完成不等于详情与评价已完成。

running用进度心跳续租；验证时清除普通执行超时、持久保存waiting_verification，暂停同一登录态的新自动工作，不因等待超过10分钟自动重派。浏览器仍在线且验证未解除时保持等待；关浏览器或网关重启后先核对扩展残留任务/标签页与领取代次，再恢复同一任务。普通执行丢失且无法核对时记expired，保留已入库和错误原因，不盲目重派；陈旧代次的结果拒收。

验证稳定消失后只在同页、同任务、同当前账号身份成立时续采；等待组件沿用docs/13。CLI已有24h/6h退避不声称覆盖扩展；未来monitor必须接入已有RiskMachine的调度闸门，存在有效退避时不排新轮，解除可见滑块也不擅自清除退避。原任务是否可续采取决于它的独立等待状态与调度闸门结果，状态条必须说明真正阻塞原因。

浏览器离线期间不累积大量补跑：每个逻辑任务最多保留一项待执行，超过时效的轮次记missed，恢复后只执行当前有效轮次。关闭任务默认停止新增排队、保留当前任务；显式取消由队列确认后结束，并保留已入库数据。页面变更、登录失效、连续失败与解析异常分别记录，不能统一写“无新账号”。

### 19.3 可观测性

任务与每次采集记录`scheduled_at/started_at/finished_at`、purpose、游戏/区服/筛选/排序、观察起止、扫描及详情尝试/成功、新增/复采/补齐、失败类别、验证次数与等待、人工介入、停止原因、预算和队列延迟。凭据、Cookie、验证令牌与卖家身份不进入日志。

效率至少区分浏览器执行耗时、验证等待、调度等待和端到端有效账号/小时；重复加载和被拒原始页不计有效账号。页面未看到的商品仅记not_observed，明确下架文案才记observed_delisted；下架与售出是不同状态，没有真实成交证据不登记成交价格。

## 20. 价格趋势数据与分析

### 20.1 同价复采必须留下观察证据

现有去重会跳过未变化商品，仅不断discover不能建立连续行情。price_refresh需在原入库管线增加明确的观察目的：即使价格未变，也写本轮价格快照和真实观察记录；同ID同轮次仍幂等，多次访问可另记真实`observed_at`，不会重复新增档案或虚构价格变动事件。

计划增加追加式`market_observation`台账，至少关联job、商品ID、实际观察时间、快照轮次、价格/可见状态、区服与筛选、配置版本、资料来源时间、raw引用及内容hash。重复回执按job与采集项身份幂等；来源页面价格与ID校验失败只写失败证据，不进入价格事实。现有`fct_listing_snapshot`仍是业务价格快照，价格变化从完整快照路径对账，不仅依赖`fct_price_change`。

复用旧资产时明确`attributes_observed_at`与新`price_observed_at`，保存价龄和资料龄；未知仍未知。列表价已更新不能把旧地图/资源写成刚核验的详情；资产是否未变未知时，该账号可以显示价格轨迹，但不进入“配置不变的价格变化”统计。不得为了复采吞吐将所有最新资料回填历史。

### 20.2 三层输出与统计门槛

1. **单账号观察**：时间、挂牌价、变动、间隔及资产状态；展示实际观察点，缺日断开，至少两次观察才计算首末变化，无需为单账号描述强凑30样本。
2. **同期间成对配置趋势**：同游戏/区服/商品类型，起止均有记录且名册/已知余额可核验一致的账号；同配置组等权，展示中位挂牌变动、样本组数、观察跨度、配对覆盖、退出/缺失量，避免一个复制配置占多票。
3. **分层固定篮子指数**：篮子与权重在基期冻结，按可比较配置和价格域汇总；纳入/退出、缺价及权重变化可复算。初期只称“试点样本挂牌指数”，分层覆盖未经证明前不称全市场趋势。

初步发布门槛：同期间至少30个有效独立配置组、固定篮子端点有效覆盖至少80%；跨日趋势试运行积累至少14个自然日，并披露实际覆盖天数。30/80%/14天是待验证的研究准入值，不是统计精度保证；低于门槛只显示观察事实与不足原因。周/月同比需要真实对应窗口，缺上期时不计算；国际服、不同游戏和币种分开计算。

未来涨跌预测后置：先扩大跨周跟踪，再用按时间前后切分、同账号/配置组隔离的独立验证，与“价格不变”及历史均值基线比较。版本更新、角色变化和资源消耗作为有来源的解释变量，不能将模型关联解释为必然折旧或因果溢价。

## 21. 高性价比评价与推荐闭环

### 21.1 先判断能否评价，再比较价格

流程：预算/区服/风险事实筛选 → 所需字段检查 → 必要详情补齐 → 当前挂牌核验 → 可比与估值评价 → 推荐结果 → 用户反馈。字段未知时进入pending_details并说明缺什么，不立即视为永久条件不匹配；已知值不满足才记rule_failed。若页面明确未公示必需字段，保留unknown并限制推荐资格，不反复补采或猜数值。

推荐资格与用户操作状态分开：`eligibility=pending_details/eligible/rule_failed/stale/source_unavailable/invalid`，`status=new/seen/ignored`继续表示用户操作。价格刷新、详情补齐、资产变更和模型发布均可触发重新评价；过期或明确下架时撤销“当前候选”资格并保留历史原因。LLM失败不能阻塞采集或资格判定，LLM也不能决定数值或改变排序。

### 21.2 三种信号分别展示

| 信号 | 依据 | 能说什么 | 不足时处理 |
|---|---|---|---|
| 条件匹配 | 用户预算、具名角色/链位/武器/资源与当前事实 | 符合所需配置 | 必需字段未知等待补齐；不称捡漏 |
| 可比挂牌优势 | 同域近似配置、可比组数与相似度、同期挂牌分布 | 比已观察可比挂牌低多少 | 保留“不足”，不用大盘最低价或跨区服填造可比 |
| 研究估值偏离 | 有效模型版本、研究价/预测带、支持域 | 当前挂牌相对研究价偏离及不确定性 | 域外无带、核心无效或漂移未核验时不发可靠低估信号 |

估值不以待估挂牌价作为输入或支持路由条件。`(研究价-挂牌价)/研究价`可作研究观察值，但不等于可套利收益；预测带下沿高于当前价且处于受支持域只能标记“需要复核的价格优势”。可比与模型明显冲突时列原因并降为待核验，不做黑箱加权消除冲突。

默认排序先按推荐资格，再按价格证据等级（可比和模型一致、单一有效证据、仅条件命中），同等级按明确的可比优势/研究偏离、价格新鲜度和ID稳定排序；证据不足不获得虚高分。偏好加权与统一0—100性价比分留到有反馈与离线验证之后，不先制定拍脑袋权重。

### 21.3 推荐卡与反馈

每条显示商品/游戏/区服、价格观察时间、资料时间、匹配条件、估值及区间/模型版本、可比数量与日期、优势依据、缺项/风险词/来源状态、理由来源和原页链接。首次入推荐列表前安排一次价格核验；默认当前价格超过24小时标stale，刷新成功才恢复。24小时为试点时效约束，后续依实测调整，不把历史数据自动叫当前优惠。

反馈提供已看、忽略及原因（不合偏好、已失效、资料有误、价格无优势、其他）；点击/收藏仅是偏好代理，不当作成交或估值准确标签。若用户记录最终购买价，保留“用户提供、未独立核验”的来源层级，不能自动并入真实成交训练集。

## 22. 估值分析、版本交接与统一入口职责

### 22.1 复用既有研究工程

未来分析消费者从生产库一致性导出一个不可变研究批次，包含截止时间、商品/快照ID、字段来源与状态、配置组、覆盖分层、raw引用、schema/rule版本和hash。批次经质量校验后进入既有wuwa-v2工程；批次完成只触发一次增量分析，不在网关请求线程内训练，不自动覆盖冻结run或原CSV，不随每批采集自动重训（§26.7）。

先批量评价新账号、支持域与残差，再决定是否需要训练。累计新配置、支持域漂移或时间段变化达到实施前登记的检查条件时才创建训练候选版本；用分组与时间隔离验证、独立校准、分域误差与预测带覆盖比较旧版本。原18.42%一次测试和19.07%冻结OOF只属于各自实验，不能充当新发布模型的成绩。发布需报告、hash校验、原子切换与回滚，未通过时保留旧版本并标记数据截止时间。

按新数据缺口回传采样优先级（哪些区服/配置/资源状态证据不足），进入同一监控预算队列；不让模型无限触发站点访问。横截面估值、已观察价格轨迹、未来价格预测分开输出，因素贡献与条件边际始终附训练域和不确定性说明。

### 22.2 界面和数据所有权

- **8765采集看板**：监控配置、启停、队列、验证等待、预算、来源覆盖、失败诊断、原始数据与查缺；继续复用现有扩展dashboard。

## 23. 按价值依赖排序的实施与验收

### 23.1 路线替代原§14以LLM为中心的交付顺序

v1.2首先按§26.8完成A—D（基线、本地优化、全文快速路径、大批验证），再进入E的定时与自动分析闭环；下表继续规定产品能力的依赖与准入，不跳过效率和完整性验证。

LLM只在结构化结果可复核后增强说明；默认不配置、不调用，模板即可完成首版。外部模型、消息发送和用户账号绑定都不是自动采集前提。网页样式优化、通用任务表单、多推送渠道和未来涨跌预测排在数据闭环之后。

### 23.2 三个主指标与诊断指标

下面阈值是试点验收设计，须在首次运行前登记，不是现有达成值；七天中失败/验证/离线不能从分母悄悄移除。

| 主指标 | 定义与来源 | 初期验收目标 | 诊断与约束 |
|---|---|---|---|
| 到期有效更新完成率 | 到期篮子ID在时限内取得身份/价格有效观察的数量 ÷ 当日开始时锁定的到期ID数量；来自任务与market_observation | 在登记运行窗口内≥95%；确实失访仍列分母并另计原因 | 看在线率、预算延期、解析失败、价格年龄P50/P95；不能用新增ID补分母 |
| 可比连续观察支持 | 给定起止窗名册/余额可核验一致的独立配置组数与固定篮子端点覆盖 | 发布趋势至少30组、覆盖≥80%、跨日试点至少14日 | 看跨日/跨周支持、未知资产、区服/价档覆盖；不足时不发布指数结论 |
| 当前推荐证据可复核率 | Top10中必需字段、当前价、优势理由、支持域与来源均可重放的条数 ÷ 实际审查条数 | 首次交付抽查最多10条须100%可复核；不足10条披露实际分母 | 不能把此数叫真实性价比准确率；另看失效撤销、误报原因、候选等待时间 |

共同护栏：重复新增/串号/错轮次/未知填0/未经校验数据发布为0；预算和串行锁不突破。七天无人值守标志必须人工介入0，另报告实际到期任务完成率与观察总时长；如果需要一次确认也只能标记有人工介入的自动调度。估值误差、预测带覆盖、域外占比是模型发布诊断指标，保留真实成交数据不足的限制，不用候选点击率替代精度。

当前这些主指标没有完整分母或运行台账，值均为未测量；本轮10/10单批质量不是七天更新完成率。完整市场覆盖率的分母未知，不发布百分比；先报告已核区服/筛选分片、分页终点、唯一账号、漏采原因和最近完整分片轮次。

### 23.3 必须覆盖的实现测试

- **任务与预算**：手动/补录/监控同时排队仍单飞；到期与时区、预算耗尽、子批不重置预算；无new的price_refresh能结束；相同ID同价跨轮有观察，同轮重复回执幂等；扫描卡数不冒充新增数。
- **恢复**：验证等待超过10分钟不被误重派；浏览器离线/重启、网关重启、取消、源页路由变化、错ID/nonce/领取代次、迟到finish全部有确定结果；验证未解除不发后续站点请求。
- **事实质量**：0/unknown/unreported分别保存；价龄与资料龄不混淆，配置变化不能进入不变篮子；未见不推断售出；原ID/价格/轮次与raw逐条核对，失败详情不计成功。

## 26. 可配置批量采集、定时更新与自动分析方案（v1.2，2026-10-13）

> 版本：v1.2；状态：方案文档已保存，功能待实施。主要数据来源：[螃蟹游戏服务网](https://www.pxb7.com/)。本节完整整合用户确认的Markdown方案，修订原§5、§6、§18和§23的固定10条设计；已有能力、历史实验和待验证路线分别说明。

### 26.1 建设目标

围绕游戏账号价格趋势、高性价比评估与推荐、账号价值估值，建设以下闭环：

**自动获取数据 → 定时监控与更新 → 完整性检查 → 自动分析 → 更新看板与推荐结果。**

采集规模由用户手动设置。此前每批10条仅为自动采集试点配置，不作为默认值、固定额度或系统上限。

本期采集完整账号介绍与公开文字字段，不下载、保存或识别图片内容。页面未公示的信息保留未知，不以推测补齐。

### 26.2 批量任务与配置

#### 26.2.1 三种任务目的

| 任务目的 | 用户设置 | 完成条件 |
|---|---|---|
| discover：新发现 | 本批新增目标N | 达到N，或到达实际列表终点、扫描预算 |
| price_refresh：价格复采 | 本批处理数量N、监控范围或选定ID | 完成该批旧账号的有效价格观察 |
| detail_enrich：详情补齐 | 本批处理数量N、缺项范围或选定ID | 完成指定账号的必要文字字段补齐 |

任务数量、扫描数量、更新数量、补齐数量、失败和重试分别统计。

#### 26.2.2 配置规则

- 任务独立设置优先；未设置时继承当前手动采集配置，不新增“默认10”。
- 开始执行时冻结本批参数，中途修改只影响下一批。
- 新增目标、处理数量、每日访问预算和执行时间分别配置。
- 当前扩展存在200条等协议边界。更大逻辑任务自动拆为执行块，总目标仍保持用户设置值，不静默截断。
- 执行块承接列表检查位置和去重状态，不重新加载相同列表反复凑数。
- 达到终点或预算不足时，报告实际完成量、未完成量和停止原因。

界面至少展示：目标规模、扫描数、新增数、更新数、文字完整数、待补齐数、失败数和当前阶段。

### 26.3 当前效率问题与研究依据

2026-10-13方案研究中的代码及已有页面只读检查确认：

1. 详情队列逐个导航商品页面，页面加载成本随账号数量累积。
2. 详情模式已经跳过列表标题补采，不能将取消标题等待作为详情模式的加速来源。
3. 当时检查的16张列表卡片中，15张介绍为160字，不能直接作为完整介绍；这是一次已有列表样本，不代表每页都相同。
4. 网关每接收一份成功详情，都会同步该游戏整份最新态CSV，存在重复查询、格式化和文件写入。
5. 现有组件已经支持观察正常商品响应、缓存完整标题，并对缺失项获取全文，可以作为优化基座。

代码依据为extension/pxb7-extension中的collection.js::navigate、content.js::ingestCurrent/runWorker、title-source.js::observe/lookup，以及pxb7/gateway.py::_apply_detail、pxb7/analysis.py::_sync_game_csv。既有全文效率调查另见[docs/07](07-全文采集效率与网络异常排查.md)。

尚未确认网站存在可返回多个商品完整介绍的批量接口。不能把批量短标题响应当作批量全文接口。旧10条试点的耗时不能按比例推导100/200条性能，未测得本方案的提速幅度。

### 26.4 推荐采集架构

默认采用以下路线：

**列表批量读取 → 完整介绍获取 → 字段核验 → 必要详情回退 → 入库 → 合并导出 → 自动分析。**

增加“自动选择采集方式”模式，同时保留现有详情模式作为回退和性能对照。

#### 26.4.1 第一层：列表基础数据

从正常列表响应及DOM取得：

- 商品ID和原页链接；
- 当前挂牌价格、区服、发布时间；
- 收藏及页面展示的基础属性；
- 可取得的完整介绍；
- 来源时间和采集范围。

列表价格先保存，不因某个账号的文字补齐失败而丢弃整批价格数据。

#### 26.4.2 第二层：完整介绍获取

按以下顺序取得完整文字：

1. 当前正常响应中已包含的完整介绍；
2. 本批已经取得并通过身份校验的文字；
3. 现有全文获取通道；
4. 详情页回退。

对已确认介绍完整且字段满足要求的账号，不再默认逐个打开详情页。

历史文字用于价格复采时保留实际资料时间。短标题相同不能证明介绍后半段未变化；到期、变化或冲突时重新获取，不将历史资料标成本轮刚核验。

#### 26.4.3 第三层：必要详情回退

以下情况进入详情队列：

- 介绍截断或来源无法确认；
- 角色、武器数量与具名明细不一致；
- 必需字段缺失；
- 不同来源存在冲突；
- 需要取得详情页独有的公开文字信息。

详情采集复用工作标签页及浏览器资源缓存。结束条件为当前商品身份、完整介绍和所需文字字段就绪，不等待图片全部加载。

就绪判断不能只看标题稳定，避免其他文字模块尚未出现就提前提交。完整介绍和页面独有字段均取得并核验后，才可标记相应字段已采集；不能通过省略必要字段获得较高完整率。

#### 26.4.4 批量接口研究

仅观察正常页面公开业务响应及平台公开文档。

若确认平台提供批量完整数据接口，且通过身份、字段覆盖和数据一致性验证，则接入同一入库管线；未确认时继续使用混合采集路线，不猜测接口、伪造请求或将候选方案写成已实现能力。

### 26.5 本地处理与存储优化

#### 26.5.1 合并CSV同步

保留现有入库事务、轮次关联和幂等校验，将CSV同步移出逐条详情的完成路径。

- 采集成功以数据库提交成功为准。
- 同游戏导出请求合并处理，运行中最多每30秒同步一次。
- 批次结束后强制同步一次。
- CSV占用或同步失败显示“数据已入库、导出待重试”。
- 导出失败不得触发重新访问商品页面。

30秒是本方案的合并同步设计值，不是现有实现或性能成绩；批末强制同步为运行中周期限制之外的终态同步。

#### 26.5.2 减少证据体积

保存：

- 完整公开介绍；
- 必要商品DOM片段或公开字段证据；
- 商品ID、来源、实际观察时间；
- 内容hash和解析版本。

不保存图片二进制、整页脚本、无关页面内容及认证信息。旧原始证据保持可读取，不因新方案自动删除。裁剪后的证据仍须能够重放解析、确认商品身份、文字完整性和字段来源；普通图片链接或数量如为必要公开元数据，可保留文字引用，不获取图片内容。

#### 26.5.3 处理衔接

本地解析、导出和分析与浏览器采集分开调度。站点访问仍由统一队列管理，避免不同任务重复访问同一商品。

### 26.6 信息完整性标准

快速路径与详情路径使用同一字段校验规则。

| 信息类别 | 校验内容 |
|---|---|
| 身份与价格 | 商品ID、原页、当前价格、实际观察时间 |
| 介绍 | 完整原文、来源、截断状态 |
| 核心属性 | 等级、黄数、角色与武器数量 |
| 资产明细 | 具名角色链位、武器精炼，与数量交叉核对 |
| 资源与交易属性 | 公示资源、区服、绑定状态、发布时间、收藏 |
| 附加文字 | 页面公示的地图、皮肤等信息 |

每个字段区分：

- 已取得；
- 明确未公示；
- 采集失败；
- 解析失败。

数值0为有效值。未知不能填0，明确未公示不能反复补采。“明确未公示”须以完整公开文字核验为依据，不能仅因列表响应缺键或标题未出现某字段就判断。资料时间与价格时间分别保存。

“公开文字采集完整”和“满足估值或推荐要求”分别判断。采全介绍不代表账号全部真实资产均已核验；用户本次确认不采图片，无法从文字核验的内容保留未知及来源限制。

### 26.7 定时更新与自动分析

复用现有浏览器扩展作为采集执行器，本地服务负责调度、质量检查和分析，统一看板提供任务管理与结果展示。管理员入口复用§25已合并的8870“采集与监控”，不另建第二套管理前台。

#### 26.7.1 定时更新

- 按用户配置的时间、范围和规模执行任务。
- 价格未变也保存本次真实观察。
- 价格时间与资料时间分别记录。
- 浏览器离线期间保留明确的延期或错过记录，不无限积压补跑。
- 中断后从已保存进度恢复，成功项不重复计入新增。

#### 26.7.2 自动分析

批次完成后触发一次增量分析，避免每新增一个账号就运行全量分析。

自动更新：

- 单账号价格轨迹；
- 满足样本门槛的同配置挂牌趋势；
- 现有模型的研究估值及支持不足提示；
- 条件匹配、可比价格优势和估值偏离证据；
- 当前候选及其新鲜度状态。

信息不足的数据可以保存观察事实，但不进入可靠估值或当前推荐。统计门槛、估值支持域和推荐证据沿用§20—§23，不通过增量触发绕过。

模型训练作为独立任务，首期不随每批采集自动重训；沿用版本校验、发布与回滚机制。

#### 26.7.3 状态展示

分别显示采集等待、浏览器离线、导出待同步、分析失败和已发布版本。采集成功不能直接视为整条分析链路成功。

### 26.8 研究与实施顺序

| 阶段 | 工作内容 | 交付证据 |
|---|---|---|
| A：测量基线 | 分阶段记录耗时、请求数、完整率和存储量 | 可复核的性能基线 |
| B：本地优化 | 合并CSV同步、证据裁剪、分阶段日志 | 相同输入下的处理成本对比 |
| C：全文快速路径 | 离线对照已有详情，再做真实小批验证 | 字段一致性与详情回退原因 |
| D：大批验证 | 分别测试100条、200条，区分首次采集和存量更新 | 吞吐、完整率、失败与回退报告 |
| E：自动闭环 | 接入定时更新、分析发布和看板刷新 | 跨日记录及七天连续观察报告 |

网络耗时可参考浏览器[资源计时接口](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceResourceTiming)。不可见的计时项标记未测量，不推测填值。列表加载、全文获取、详情导航、解析、数据库提交、CSV导出和端到端耗时分开记录；100/200是实验对照规模，不是用户批量的固定额度。

### 26.9 验收标准

#### 26.9.1 数量与完整性

- 用户设置值与实际逻辑任务目标一致。
- 跨执行块无丢失、重复新增或错误计数。
- 与详情对照的公开文字字段无静默遗漏、串号或未知填0。
- 未公示、下架、失败和未完成数量单独披露。

#### 26.9.2 效率

分别报告：

- 有效完整账号/分钟；
- 整批端到端耗时；
- 详情回退比例；
- 站点请求次数；
- CSV同步次数与耗时；
- 新增证据存储量；
- 验证等待及人工介入。

将“大批量有效吞吐至少提高一倍”作为研究目标，未达成时保留真实测量结果，不预先承诺提速幅度。相同完整性口径下比较有效账号数量与耗时，不以请求结束、解析成功或字段减少冒充有效完整账号。

#### 26.9.3 回归场景

### 28.7 请求诊断与访问恢复（C0）

每次尝试记录商品/批次、来源、fetch/body/validate阶段、尝试序号、耗时、HTTP状态、内容类型、异常枚举及可读取的Retry-After；只保存白名单诊断，不保存头、Cookie、验证码参数或任意响应/异常正文。

| 分类 | 判定与处理 |
| --- | --- |
| `timeout` | 本脚本主动超时；有限退避，不写成CORS或验证 |
| `fetch-rejected` | Fetch拒绝；原因未明，记录未确认，不自动判定站点限流 |
| `invalid-json` / `unexpected-content` | 解析失败/未知非JSON；已明确挑战证据则另归verification，不把所有HTML视为滑块 |
| `business-error` / `empty-title` | 业务失败/无全文；保留缺项，可按目的进入详情，不伪装成功 |
| `auth-required` / `access-denied` | 401/403；阻止后续主动访问并提示访问处理；没有可见挑战不启动自动滑块 |
| `rate-limit` | 429，读取得到恢复时间则持久记录并遵守；读不到标记未知，不猜服务端时间 |
| `verification` | 可见挑战或已确认挑战响应；进入已有验证处理流程，输入回执与解除、业务恢复分开记 |
| `route-change` / `cancelled` | 终止旧读取，拒收过期回执，不计作网站失败 |

整个逻辑任务的每商品尝试预算统一计算，不能MAIN两次加外层两次再加详情重试而不计成本。冷却/访问等待有明确状态和下一执行条件，不能永久等一个误分类的“滑块”。跨源计时或浏览器错误不可见的项目记未测量。

### 28.8 CSV合并与本地工作（C1）

数据库提交成功后在同一事务中推进受影响游戏dirty_generation；提交回执立即返回“已入库、导出待同步”。已有CSV格式、路径、原子临时文件替换及错误状态沿用analysis.py。

导出协调器用自己的数据库连接，不能把采集线程conn传给后台线程；沿用DuckDB单写者与PL.run_lock纪律，核对网关state.lock锁顺序，不在长导出中持有不必要的全局锁。每游戏运行中至多30秒同步一次，批末/取消/部分终态执行一次强制flush，空闲到期亦flush。

导出以generation确认完成：导出期间有新入库时不能清掉新dirty状态。进程重启扫描未导出的代次，CSV被占用或错误保留dirty并本地重试；不得重新触发站点访问。批末flush携带批次幂等键，网络回执丢失不重复导出同一目标代次。分析只读取满足该批截止代次的导出/数据库交接，不把旧CSV显示为最新。

证据裁剪后必须保留解析需要的商品主体、公开文字、ID/游戏识别、字段来源和完整性依据。旧raw不删除；用新旧证据离线重放比较字段/hash后才启用裁剪，不能只保存介绍而丢失详情独有文字模块。

### 28.9 持久全文缓存（C3）

采用本机网关有界缓存，复用现有DuckDB持久化，不保存认证数据。缓存身份至少校验game_id、字符串listing_id、页面商品编号与内容来源；当前短标题前缀只是拒错依据，不能作为后半段未变的证明。

优先读取本次正常响应完整原文，再查有效历史全文。过期、编号/游戏冲突、明确force刷新、前缀变化或质量版本不兼容均不命中。新响应优先，晚到旧内容按实际观察时间和代次拒绝覆盖；内容冲突进入待核验，不任选一个成功。

缓存命中输出原取得时间、来源和reuse标志，当前价格仍独立观察。某字段取自历史资料时保留字段级来源时间；没有实际全页资料核验时，不能把账户整体标为本轮完整核验。

缓存容量、最长全文和批量查询ID数设有明确上限，实施前登记候选值并用内存/响应体积测量确认；淘汰按过期与最近使用，容量满不能清空成功入库数据。先离线索引既有公开全文构建缓存，不重新访问全部存量商品；来源时间未知的旧资料只用于研究对照，不能当有效新鲜缓存。

### 28.10 自动混合采集与完整性（C4）

自动模式先提交列表事实，再按商品决定路径：本次完整文字 → 有效历史文字 → 必要全文请求 → 必要详情。当前明确缺失或来源不可靠时保留待补项。详情模式继续直接逐项打开，不额外增加列表全文请求。

共享的网关质量函数基于现有backfill.missing、武器状态及名册规则扩展，输出：介绍完整状态、字段状态、资料来源/时间、详情回退原因和估值可用状态。字段区分取得、明确未公示、采集失败、解析失败；0是值，unknown不是0。各游戏按画像检查，不能把鸣潮词表要求套给其他游戏。

自动路径仅在所需字段均满足时结束；完整介绍不代表所有详情独有字段就绪。详情就绪由身份、完整介绍及必需模块共同判断：模块稳定/明确未公示需要证据，超时只记缺项。图片不参与等待。原轮次价格保持，详情当时显示的新价格若要作为新观察必须走price_refresh契约，不能偷偷覆盖补录价格。

异步全文提交关联(batch_id, listing_id, snapshot_round, claim_epoch)及资料观察时间，复用现有解析/事实/修订事务，不新开旁路写库。字段合并保留较新有效值和未公示依据，冲突单独披露，不能用缓存覆盖本批取得的新完整内容。

### 28.11 三类目的、访问队列与分块（C5）

- **discover**：维持全库ID去重；旧号可更新/补齐但不消耗新增目标。扫描和访问预算耗尽、列表实际终点或目标满足时停止，报告不足。
- **price_refresh**：按选定ID或冻结监控范围核验当前价格。已有完整同价账号也需真实观察，不能被旧skip过滤；同价不造变价事件，价格变化才入事件台账。未观察到的ID记not-seen/未完成，不能推断下架或售出。
- **detail_enrich**：明确字段依赖及原快照轮次，满足要求或已证实未公示的ID跳过；仅缺项/过期/冲突进入补齐，独立于一次自动重试资格，不无限消耗同商品。

后台统一授权采集器产生的扩页、全文、详情访问，按站点/会话单并发，所有来源共享忙碌锁。授权携带一次permit_id、有效期、批次与商品；执行前校验，取消/验证/限流收回未使用授权。页面会话执行实际业务请求，完成/失败回执释放授权；Permit丢失或超时先对账再恢复，不立刻重发未知结果。

主动操作预算在发出前扣计，失败尝试不退回已消耗额度。一次详情导航或扩页可引发多条网站请求，必须分别统计“受控主动操作数”和“可观测实际HTTP尝试”；不可观测的页面自发请求记覆盖未知，不能宣称队列控制了浏览器全部请求或绕开站点累计频率。

大逻辑任务按≤200唯一商品执行块推进，保存已扫描ID、已成功ID、尚待ID、真实页面位置/已验证cursor、预算与轮次。当前页面连续扩页时不重载首屏；刷新丢失位置若无已验证的续页能力，进入needs_reconcile并报告恢复成本，不能猜page参数或承诺直接定位。确需重新扫描时已成功项不补请求、不重新计新增，重扫成本仍计预算。缺少分页终点证据时只能报告覆盖未知。

### 28.12 滑块处理与任务恢复

沿用v0.5.14的一次普通滑块策略。增加事件：challenge_detected、input_attempted、input_sent/unsupported/input_failed、challenge_cleared、business_ready、item_committed；保存阶段、商品、等待时长与是否人工介入。最后两项必须独立核验，不能通过input_sent或按钮文字直接增加成功账号数。

waiting_verification期间保存当前项/队列/代次与原轮次，普通10分钟执行租约不将它判为过期；阻止同一会话新任务抢占现场。本地解析、导出和已完成数据分析仍可执行。取消或错页终止旧输入；恢复前核对扩展任务、当前URL和网关批次，过期代次拒收。

自动输入失败后不循环拖动、不刷新验证页。若用户未确认已完成且未观察到挑战解除，保持等待；公开挑战支持范围外记录unsupported。七天测试分别记录自动成功与人工完成，不能把人工兜底批次算成零人工运行。

### 28.13 定时采集与批末分析衔接（C7）

任务定义仍以tasks.yaml为源，界面启停/运行覆写沿用§5约定，不另建冲突配置源。定时due_job与collection_batch一一关联，到期先检查浏览器在线、既有执行/验证、活动时段和预算，再有界领取；旧实例与新实例不能并行消费同一任务。

新增时间明确存储为UTC并标明语义，界面按Asia/Shanghai展示；旧快照时间不在本次迁移中盲目转换。页面观察时间、网关接收时间、资料原取得时间、批次时间分别保存，跨进程耗时不由两个未校准时钟直接相减。

浏览器离线记录deferred/missed及原因；错过任务按预先配置的合并/过期策略处理，不无限补跑。普通执行租约丢失先对账，验证等待单独恢复。统一看板显示冻结配置、三个purpose、预算、来源覆盖、采集/补齐/导出/交接各阶段，保留部分成功。

批末以(batch_id, cutoff_generation)触发一次交接，重试只处理交接，不重采商品。CSV尚未达到该截止代次时等待同步；分析失败显示handoff_failed并保留旧发布。是否使用导出文件或数据库只读快照需在C7接线前按现有估值工程契约冻结，不把“已入库”当作“分析已发布”。本期不随批次自动重训。

### 29.4 台账、导出与恢复

新增`collection_batch`、`collection_batch_item`、`collection_observation`、`collection_scanned`、`collection_access`、`listing_text_cache`、`collection_export_state`、`collection_site_hold`及`monitor_job`。在`run_lock`内升级；有历史快照时先checkpoint、关闭连接、备份，然后事务建表。旧快照与旧raw不删除、不转换原时间口径；新批次、观察、缓存和调度时间使用UTC，看板按上海时间展示。当前代码尚未在生产库执行该迁移。

新协议固定路由包括`/collection/batch/create|progress|access|flush`、`/collection/text`、`/collection/text-cache/query|store`、`/collection/monitor/claim`。仅扩展和本机页面调用新的本地动作路由；商品写入核对协议版本、有效批次/代次、范围、游戏、商品ID、原轮次和最新轮次，拒收过期回执。公开文字证据移除脚本、表单、认证属性与图片内容，保留解析所需公开语义及隐藏模板标记、内容hash；旧证据保持可读取。

| 情况 | 已实现处理 |
| --- | --- |
| CSV占用/导出失败 | 保留dirty代次、定时本地重试；看板“重试本地导出与分析”不访问商品 |
| 全文/状态提交重传 | 价格观察唯一键，同内容/来源/时间的全文重传不再写修订或推进导出；已确认终态不重开 |
| 网关回执丢失 | 扩展保留状态待补报，状态轮询/下次任务/定时领取先补报，不重访已成功商品 |
| 列表重载且位置丢失 | `needs_reconcile`，成功事实保留，显式对账后取消；不猜分页参数恢复 |
| 普通执行超过10分钟无心跳 | 创建/领取前转`needs_reconcile`，本地对账取消入口可释放遗失任务 |
| 可见访问验证 | 沿用v0.5.14配置与一次普通滑块处理，等待状态不因普通租约超时失效，不抢占现场 |
| 429 | 可读Retry-After持久保存，时间未到不能提前解除；不可读标为恢复时间未知 |
| 401/403/未知非JSON | 记录明确分类并暂停后续主动访问；本机看板提供确认网站可访问后的解除等待入口 |
| 数据路径变更 | 活动批次期间拒绝；无活动批次时先同步旧位置，再为新位置绑定导出协调器 |

新全文诊断保留商品ID、阶段、尝试序号、耗时、HTTP状态、内容类型类别、异常枚举和可读恢复时间，不保存认证头或任意响应/异常正文。检查点仅保留最近200条诊断/事件，不能把这部分日志当全部HTTP请求数。可见挑战、输入尝试、挑战解除、商品提交等分别记录；人工介入未可靠判定时标未知，不能计为零人工。

新批次与既有补录共享扩展忙碌队列；授权记录当前按发出前计费，尚未实现§28所拟议的每份permit完成回执/跨浏览器租约对账。正常页面自发请求和预检也不能全部观测，因此必须区分主动操作与实际HTTP覆盖。

### 29.5 定时采集与分析交接

仅在`config/tasks.yaml`某任务下显式增加有效`monitor`配置时启用；任务本身还须enabled，并属于当前勾选的游戏范围。未配置或`enabled: false`完全关闭。以下只是示例，**本轮未写入生产配置**：

```yaml
# 放在既有wuwa_official任务的字段下；规模与预算由用户设置
monitor:
  enabled: true
  interval_minutes: 360
  purpose: price_refresh
  target_count: 100
  scan_budget: 3200
  max_scan_rounds: 12
  daily_access_budget: 500
  source_url: https://www.pxb7.com/buy/10302
  ids: []
```

保留现有每任务每日最多4轮档位（间隔至少360分钟），按UTC时间槽记录due job；网关每30秒登记到期/离线状态，扩展空闲报警轮询领取并打开一个工作列表页。浏览器离线记录deferred，较旧未领轮次转missed并合并数量，只保留最新待执行轮次，不无限补跑。没有恢复浏览器进程、电脑睡眠或关闭浏览器后的执行能力。

批末先核对该批截止导出代次，再更新已有数据库趋势/质量分析视图；成功结果持久保存，重复flush不重复交接，失败可单独重试。估值模型训练、研究版发布、推荐版本的8870交接仍走现有流程；没有新接通自动估值发布、模型重训或可靠推荐全链路。任意活动时段/错过策略的界面编辑也仍待后续实现，本期采用固定的最新轮次合并策略。
