# 列表与详情采集浏览器对比实验

日期：2026-10-04。浏览器：用户现有 Chrome 会话。扩展：0.4.5。

## 实测结果

对同一组 16 个鸣潮商品进行比较，全部是列表中约 160 字的截断标题，均需补取武器全文。

| 方式 | 实测读取耗时 | 完整标题 | 武器数量与精炼 | 失败 |
| --- | --- | --- | --- | --- |
| 当前扩展在列表补全文，2 秒间隔 | 46.420 秒 | 8/16 | 前 8 条取得 | 后 3 个商品的 6 次尝试均在预检失败，剩余 5 个未尝试 |
| 浏览器串行打开对应详情，标题就绪即读取，不加固定间隔 | 32.326 秒 | 16/16 | 16 条均取得，精炼条目数与武器数相等 | 无标题超时或可见验证 |

详情单页中位耗时 1.998 秒。列表取得的 8 条全文与对应详情去除商品编号前缀、标点空白后的全文完全一致；详情的 16 条均匹配原列表短标题前缀及明确的“详情看图”结尾。

列表的 46.420 秒是第一条标题 POST 尝试开始至最后一次失败结束的 DevTools 单调时间差。详情的 32.326 秒是 16 次“导航 → 主标题可见 → 读取 DOM”的协调器耗时总和。工具调用之间的人为分析时间未计入详情总和，浏览器操作自身的开销包含在内。两者均不是生产入库端到端耗时，未把列表初始加载、本机解析入库或现有详情插件额外等待计入比较。

因此，本次样本中详情读取耗时少约 30.4%，并取得两倍的完整商品数；这不是对所有商品或长期运行的速度保证。

## 已抓到的失败机制

列表组无成功缓存命中，实际有 14 次标题 POST 尝试，每次均观察到对应 OPTIONS 预检：

- 前 8 次：预检 200，标题 POST 200，JSON 返回有效全文。
- 第 9 个商品开始：3 个商品各尝试两次，6 次 OPTIONS 返回 405、`text/html`。
- 对应 POST 被浏览器以 `net::ERR_FAILED` 结束，DevTools 明确记录 `corsErrorStatus.corsError = PreflightInvalidStatus`。
- 不应把这些记录表述为 14 次标题 POST 都成功发到业务服务；6 次在预检阶段被阻止。扩展看到的是 Fetch 拒绝，所以记为 `network-error`，而不是能够读取的 HTTP 405。
- 常规站点列表请求与扩展标题请求都经过页面现有 Fetch 包装，均观察到站点附加的校验查询参数及相同类型的请求头。只保存参数名/请求头名的比较结论，不保存其值。没有证据证明扩展缺少整个页面请求包装，也不能据此确定精确的限流额度。

预检失败已经确认；405 是限流、访问校验还是接口特定策略仍需进一步证据。详情路径成功说明其正常页面加载流程在本次条件下未受同样影响；不能据此推断详情永不触发验证。

## 实验过程与范围

1. 先做一组详情试读：另外 16 个商品全部取得全文，累计 32.040 秒。它用于确认选择器和正常导航可行，不混入同组对比统计。
2. 尝试自动启动列表对照时，临时开启自动采集；启动过程出现拦截页拒收，没有有效标题请求，这次准备过程不计入有效列表对照。
3. 已恢复原配置，随后用户手动触发当前列表采集。实际列表与最初锁定的商品发生变化，因此以这次真实请求的商品编号和当前 DOM 的 16 个 ID 重新锁定样本。
4. 从已经观察到的成功标题响应中读取公开全文，记录预检失败；未重发接口请求。再串行正常导航到同一组 16 个详情，并从 `.product-detail` 主标题读取文本。
5. 主标题虽可能被 CSS 折叠，但全文已在 DOM，实验计时不要求点击“更多”、读取截图或运行 OCR。最后一次展开仅用于展示证据，不计入采集耗时。
6. 未绕过验证码、未增加并发、未修改采集脚本。实验临时设置已恢复：自动采集关闭、全文间隔 2 秒，其余值与备份一致。详情实验只保存本机实验文本，不写生产快照；有效列表组未出现新的成功入库 raw，不能把网页全文取得等同于已经入库。
7. 已关闭本次 Network 诊断。实验响应仅提取公开标题、商品关联、状态及时间，不保存认证头、Cookie 或校验参数值。

## 推荐的新方案

采用“列表获取商品清单和价格 → 缺全文商品进入详情队列 → 一个后台标签页串行处理”的方式。保留列表缓存命中路径；首次采集和缺失商品优先走正常详情导航，不再对每张商品补发标题接口请求。

详情采集以商品 ID、主标题存在、前缀匹配、完整结尾和短时稳定性判断就绪，不依赖每页固定等 2.5 秒，更不使用 5 秒固定间隔。保留可配置超时；遇到验证停止并保留队列，页面跳转或商品 ID 不符拒收。没有完整结尾的正常商品应保留明确的“完整性未确认”状态，不能强行算成功。

当前插件的详情入口本身还有 SPA 等待 2.5 秒和标题稳定等待。原样逐个打开并自动入库会额外花时间，不能直接套用此次 32.326 秒。新队列应按页面就绪触发采集，复用已有解析器，并保存到原列表采集任务对应轮次及详情实际取得时间。

详情页会加载图片、推荐和更多资源，流量成本高于单一标题接口。生产实现先保持一个标签页、并发 1；以最终入库耗时与完整率验收，另做较大但有界样本，记录超时、验证发生率和资源开销。本次暖浏览器环境、非随机顺序的一组对比不能用于保证千条商品持续吞吐量，也不能将未经确认的批量详情导航直接投入长期自动运行。
