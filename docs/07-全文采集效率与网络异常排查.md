# 全文采集效率与网络异常排查

调查日期：2026-10-04，扩展版本：0.4.5。本次交付为排查结果和实施方案，没有修改运行代码或采集配置。

## 已确认的事实

### 生产批次不能证明固定频率阈值

| 原始批次 | 配置间隔 | 全文取得 | 补请求商品数 | HTTP 尝试数 | 结果 |
| --- | --- | --- | --- | --- | --- |
| `wuwa_official-plugin-20261004T135152-6371` | 5 秒 | 16/16 | 8 | 8 | 完成，无错误 |
| `wuwa_official-plugin-20261004T135554-1814` | 4 秒 | 8/16 | 11 | 14 | 3 个商品各失败 2 次，`network-error`，随后熔断 |

路径前缀：`data/raw/pxb7/wuwa_official/20261004/`，元数据文件均为 `list_p01.json`。

5 秒批次中的另 8 张未补发请求。因此两次不是同请求数量、同缓存状态的对照实验，不能推导出“5 秒安全、4 秒过快”，更不能据此认定网站有精确的 8 请求阈值。当前用户配置已改为 2 秒，自动采集关闭；本次保持原值。

### 网站自身也会收到访问验证响应

通过 Chrome 正常刷新已有鸣潮列表页，仅观察网站请求，未启动扩展整页采集、未发送额外标题请求、未解验证码：

- `/api/search/product/v2/selectSearchPageList` 有 HTTP 200、`text/html` 响应，响应含 WAF/访问验证标记，随后也有正常 JSON 响应。HTTP 200 不等于接口成功返回商品数据。
- 检查一份成功 JSON 的 16 条商品，`productName` 全部为空，`showTitle` 全部为 160 字。这个样本不能用列表响应直接恢复全部武器全文。当前被动缓存仍应保留，但不能假定它每页都能命中。
- 页面最终有 16 张、16 个唯一商品 ID，访问验证容器隐藏。仅凭验证码节点存在不能认定正在验证。
- 观察到的 `ERR_CONNECTION_CLOSED` 对应阿里云验证码上传请求；`ERR_ABORTED` 包含统计请求。它们没有与上次失败的标题请求对应，不能拿来解释那 3 个 `network-error`。
- 结束后已关闭此次 Network 诊断。没有保存认证头、Cookie、验证码参数或原始业务响应。

以上确认网站请求链路会经过访问验证，但没有重现上次标题请求失败，不能把全部失败归因于 WAF、CORS 或限流。

## 为什么缩短间隔可能增加失败

请求更密集会提高单位时间内的接口调用量；限流也可能按 IP、会话、接口或滑动时间窗计算，而不是只看相邻两次间隔。用户浏览、页面预加载和其他标签页也可能贡献请求。项目当前的节流状态仅在一个页面内，不能控制其他标签页。

跨源请求还存在预检、会话和访问验证响应的问题。浏览器在无法向脚本暴露响应时可能表现为 Fetch 的网络错误，而不一定给脚本可见的 429/403。普通断网、连接中断和主动超时也会进入异常路径。这些是候选机制；标题请求的具体失败机制仍需关联证据。

参考：[MDN Fetch 跨源凭据与预检](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch)、[HTTP 429](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/429)。

## 当前代码中可直接优化的地方

1. `title-source.js` 的 `catch` 将 Fetch 拒绝、15 秒主动超时以及 `response.json()` 失败统一写为 `network-error`，且异常中的 HTTP 状态不保留。现有日志无法区分原因。
2. 每个失败商品可在 MAIN 请求两次，再在整页补采一轮请求两次，最多 4 次 HTTP 尝试。三次持续网络失败会停止整页；此时不执行第二轮。不能把每次重试都当作提高效率。
3. 缓存仅在页面内存中，最多 500 条、10 分钟，刷新后消失。已采过同一商品在后续轮次、刷新或新标签页中可能再次逐项获取全文。
4. 成功请求也始终等待固定间隔，并每 8 次尝试暂停。两种等待取较大值，不是简单相加，但即使无错误也会降低吞吐量。
5. `titles.js` 将所有含抽卡关键词的卡片加入全文队列；已在短文案中出现明确完整结尾的商品也会进入 MAIN，缓存未命中时仍可能补发请求。

## 建议实施方案

### 第一阶段：把失败分类和请求成本测清楚

新增有限、结构化诊断字段：请求阶段（fetch/body/validate）、耗时、HTTP 状态、响应类型、异常类别、是否由本脚本超时、来源（列表缓存/历史缓存/标题接口）、可读取的 `Retry-After`。异常仅保存白名单类别，不记录任意错误正文、请求头或带查询参数的 URL。

将主动超时记为 `timeout`，JSON 解析失败记为 `invalid-json`，Fetch 拒绝记为 `fetch-rejected`。Fetch 本身不能可靠区分 CORS 与断网；必要时短时使用 DevTools 将具体请求的 `loadingFailed/corsErrorStatus` 与商品对应，不把猜测写成日志事实。

对 HTML/401/403/可见验证立即停止全文补请求，保留已入库数据与待补清单。429 停止该站点补采队列，若能读取 `Retry-After`，设置不可早于它的恢复时间；不要在响应不可见时猜测该头的值。参考：[Retry-After](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Retry-After)。

### 第二阶段：优先减少请求数量

以商品 ID + 商品编号 + 游戏 + 当前短标题指纹关联全文，将成功的公开全文保存在本机有界缓存中，跨刷新和标签页复用。保留全文取得时间、来源、有效期，禁止缓存认证信息。

价格/收藏等易变字段按每轮正常采集；全文仅对新增、缺失、过期或短标题变化的商品补采。缓存命中应再次校验商品和前缀。短标题相同不能保证后面的武器段没变化，因此缓存有效期必须有限，并明确标记复用时间，允许强制刷新；不能将旧全文伪装成本轮刚确认的属性。

候选有效期可从 30 分钟开始验证，并由实际标题变更率调整；这是实施参数建议，不是已证明账号内容在 30 分钟内不变。先用已有 raw/完整标题建立缓存索引，不需要重发全部请求。

对短文案已有明确完整结尾的商品直接校验和复用。不能仅凭出现“五星武器”等关键词、字数较短或黄数关系就推断全文完整；采用项目既有的“详情看图/官方截图”等明确结尾和分段规则。

### 第三阶段：先入库列表，独立补齐队列

列表价格采集与全文补齐分开：先保存当前轮次的列表数据，把缺全文商品放入有界队列。队列优先新增/缺失，按商品去重，并保存失败次数和下次可尝试时间。单个失败不阻塞其他列表数据入库；网站验证/限流触发站点级暂停。

补齐结果写回原始采集任务的轮次，并保留全文实际取得时间，不能把晚到结果关联到用户已经切换的商品，也不能用旧缓存覆盖新的完整标题。界面分别显示列表完成数、全文完成数、待补数，避免“解析率 100%”被理解为武器完整率 100%。不因拆队列而无限加载更多：同样保留张数上限和站点暂停状态。

多个标签页通过扩展后台协调同一站点的请求预算。后台负责排队/授权时间，具体请求仍在正常站点页面会话内完成；没有必要为此改成后台直连网站或新增广泛站点权限。

### 第四阶段：在数据支持下使用自适应间隔

保持单请求并发，从当前配置的 2 秒作为候选起点。用成功率和响应耗时控制速度：连续成功时逐步恢复较短间隔；超时/5xx 时只对受影响请求有限退避，并在恢复后先放行一个请求确认；验证码/访问验证停止，等待正常验证完成。429 遵守服务端恢复时间。

当前每 8 请求强制暂停可在诊断数据足够后改为滚动窗口预算，避免成功时无条件多等。但不能预先宣称某个窗口额度是网站允许值。将间隔按请求开始时间控制，同时保持并发为 1，可以避免慢响应完成后再额外等整段时间；遇到错误仍应用完成后的冷却时间。

不建议直接增加并发。首次采集的新商品如果只能逐项获取全文，在网站约束不变时存在真实的吞吐上限。尚未发现可返回多个商品完整标题的批量接口，不能把已观察的批量短标题响应当作批量全文方案。

## 效率估算与验收

以下仅为 v0.4.5 等待逻辑的计算值，假定无缓存、无错误、从空闲状态开始，不含接口响应耗时、浏览器调度和页面加载耗时：

| 待补全文数 | 5 秒固定间隔 | 2 秒固定间隔 |
| --- | --- | --- |
| 16 | 80 秒 | 36 秒 |
| 200 | 1115 秒（约 18.6 分钟） | 542 秒（约 9.0 分钟） |

公式：`(N-1) × 间隔 + floor((N-1)/8) × (max(8秒,2×间隔)-间隔)`。如果缓存使 200 张中只剩 20 张需要补请求，则额外请求数量减少 90%；整体耗时降低比例还取决于页面加载等成本，不等于实测提速 90%。

验收用相同数量、可比缓存状态的少量真实商品，记录：新增 HTTP 尝试数、缓存命中、全文完整率、每个请求的失败类别、重试成本、耗时中位数/较慢分位数和整批耗时。先验证请求分类和缓存准确性，再逐步缩短间隔；遇到验证/429 即停止该组，不反复施压测试。离线回归覆盖缓存失效、错号拒收、路由切换、晚到结果关联、队列暂停/恢复和旧全文不覆盖新全文。

推荐顺序：诊断细分 → 跨轮缓存与只补缺项 → 采集/补齐分离 → 有证据的自适应节流。固定 5 秒可作为临时保守策略，不能作为长期效率方案或已证明的安全阈值。

### 调查范围与结论

读取“研究滑块验证应对方案”聊天（`01a12bf9-45f5-7c73-8399-6d78e0cf6313`）、docs/13和docs/27，核对当前扩展与网关。使用Exa在验证机制、WAF频率策略、pxb7开放渠道、浏览器输入四个方向检索30条结果，去除二手宣传、商业打码成功率和与市场读取无关的商家发布接口，只把官方文档用作技术依据。

### 方向一：减少验证出现的机会

优先减少同一业务目标所需的站点请求，而不是缩短间隔或加并发：

1. **列表先保存观察事实**：价格、ID、区服与时间先入库。明确标记介绍截断和缺失字段，失败全文不丢整批价格，也不把“解析成功”标为“武器信息完整”。
2. **完整介绍优先复用**：先读页面正常业务响应中已存在的完整介绍，再用本批缓存；构建有界的本机跨轮缓存，仅保存公开文字、ID、来源、hash及取得时间。当前缓存只活在页面内，持久缓存还未实施。短标题相同不能证明武器段没变，必须设置资料有效期并支持强制刷新。
3. **详情仅用于必要补齐**：新增、过期、截断、字段冲突或详情独有文字进入补齐队列；明确未公示的字段不重复补采。价格复采与完整资料刷新分开，避免每次看价格都打开每个详情。
4. **统一调度访问**：扩页、标题补采、详情和多个任务共享单一队列与滚动请求预算。按新增数停止和按覆盖范围停止是两种目的；全市场更新需独立的分页终点与ID覆盖台账，不能靠每次200条新增证明完成全量。
5. **诊断后再调节速度**：记录fetch/body/validate阶段、耗时、HTTP状态、内容类型和可读取的`Retry-After`，分别记timeout、fetch-rejected、invalid-json、business-error和明确challenge。只保存白名单类别，认证信息与任意异常正文不落盘。Fetch拒绝本身不能区分断网与CORS，必要时短时关联浏览器网络错误。
6. **本地处理不占访问队列**：同游戏CSV合并同步，批次结束强制导出；数据库成功但CSV失败只重试本地导出，避免为导出错误再次访问商品。解析、导出和分析可处理已取得的数据，不必因滑块等待全部停工。

阿里云官方WAF规则可以按IP、会话、账号或参数累计窗口频率；普通滑块与严格滑块的放行方式也不同。因此不能承诺“固定每N秒就不出滑块”，也不能套用其默认放行时间作为pxb7实际有效期。[阿里云WAF自定义规则](https://help.aliyun.com/zh/waf/web-application-firewall-3-0/user-guide/configure-custom-rules-to-defend-against-specific-requests)

更高吞吐且长期无人值守的方向是确认平台授权的批量资料或数据合作。WAF白名单需网站运营方设置，客户端不能替平台配置。本轮搜索没有确认公开的全市场批量完整介绍API；搜索出现的商家商品发布文档不支持该结论。[WAF白名单说明](https://help.aliyun.com/zh/waf/web-application-firewall-3-0/user-guide/configure-whitelist-rules-to-allow-specific-requests)

### 方向二：自行完成页面验证

| 方法 | 判断 | 当前实施状态 |
| --- | --- | --- |
| 内容脚本dispatchEvent模拟拖动 | 事件由脚本分发时`isTrusted`为false，不应把事件发出等同于真实输入或网站接受 | 不作为首选实现；[MDN事件说明](https://developer.mozilla.org/en-US/docs/Web/API/Event/isTrusted) |
| 当前扩展用浏览器Input进行普通拖动 | 不需要外部付费求解，也不需要识别拼图；对应已观察的“拖到最右端”形态 | v0.5.14已接入可配置一次输入、任务校验与失败人工兜底，离线已覆盖；在线接受率未测 |
| Windows原生鼠标操作 | 可沿用真实浏览器，但前台切换、窗口遮挡和坐标变化增加维护成本 | 研究备选，未加入常驻执行器 |
| 拼图识别或视觉模型 | 只解决目标位置，不能保证设备/频率/行为判定通过；当前普通滑块并无拼图 | 本次不实现，遇到形态变化保留现场并归为unsupported |
| 平台白名单/授权渠道 | 由平台调整访问或验证策略，最适合稳定持续数据渠道 | 待确认合作能力，未联系或申请 |

v0.5.14不再仅等待人工：配置`verification_mode=auto_slider`后，进入验证处理、保存队列、尝试一次输入，然后观察挑战稳定消失，仍由原采集逻辑检查商品身份、标题和入库结果。未观察到可见挑战时不会凭网关拒收启动盲目拖动；刷新或后台重启不会重复当前事件。仅解除挑战不会跳过当前商品，也不会把旧资料标为本轮新取得。

阿里云的验证结果可能来自访问频率、设备或模拟滑动行为等多种因素；这解释为什么“已经拖到右边”仍可能失败，但并不能据此推断pxb7使用了哪条策略。本地固定匀速拖动是实验实现，没有伪造人类轨迹；如果被服务端拒绝，下一步应记录接受率和失败条件，再决定是否值得继续投入。[官方返回结果说明](https://help.aliyun.com/zh/captcha/captcha2-0/user-guide/description-of-data-returned-by-the-client)
