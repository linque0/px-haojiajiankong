## 7. 扩展双采集模式与进度（原 docs/09-扩展双采集模式与进度.md 整并入此）

### 7.1 使用

1. 在扩展弹窗点「应用扩展更新」，然后刷新 pxb7 列表页。
2. 选择「列表采集」或「详情页采集」，填写 1～200 的任意整数张数。默认仍是列表模式、16 张，原有自动开关、目标游戏和全文请求间隔均保留。
3. 点「采集本页」会先保存当前设置，再开始任务；也可单独保存设置用于后续自动采集。任务开始后切换设置用于下一次采集；需要中止当前任务时点「取消采集」。

两种模式都从当前列表选前 N 个唯一商品，不再把整个列表的超额卡片或推荐位一起入库。数量不足时滚动或点击站点加载控件，连续两轮无新增/达到轮次上限则停止，并显示实际加载数量。当前页面本身为详情时，只采当前商品。

### 7.2 两种方式

| 方式 | 行为 | 等待 |
| --- | --- | --- |
| 列表采集 | 复用列表全文；缺失时按编号补请求，上传一次选中卡片的 DOM 副本 | 继续遵守用户设置的全文请求间隔、重试与暂停规则 |
| 详情页采集 | 先入库列表价格和清单，再复用一个后台标签页，串行正常打开页面中的详情链接，读取主标题和详情字段 | 观察主标题就绪与短时稳定性；详情采集间隔（第 2 张起生效）独立于全文请求间隔；不加每张 5 秒或 SPA 固定等待 |

详情标题按列表短标题前缀校验，拒绝错号/截断内容；支持标题折叠及展开。主标题最长观察约 20 秒，每页 60 秒无响应则记录失败并继续；连续 3 张失败或收到验证/拦截信号会暂停，保留最后的标签页供检查。网站未完整公示武器数量/精炼时显示待补齐，不算全部完成。

队列保存商品 ID、页面公开链接、短标题、原列表轮次及进度，不保存认证头或 Cookie。通过内容脚本消息推进下一张，弹窗关闭、MV3 服务工作线程休眠/恢复不会依赖原弹窗的 Promise。浏览器关闭、工作标签页关闭或任务超时会报告结束/取消状态；暂停后完成网站验证并返回列表重新采集。采集中不自动重载扩展更新。

详情只回填原列表批次的快照轮次；跨过半小时边界也不会写到后来新建的快照。详情实际取得时间仍在 raw 元数据记录。原轮次不存在则拒绝回填，不把旧详情挂到下一批数据。

### 7.3 设置解释

- **去重间隔**：同一标签页会话内，同一网址成功自动采集后再次自动采集的最短间隔。手动采集忽略它；失败/部分完成不设成功去重标记。它不是商品之间的等待。
- **SPA 等待**：站内路由变化后为渲染预留的等待。普通首次自动采集也沿用此值；详情队列直接观察主标题就绪，不逐张应用。
- **全文请求间隔**：仅用于列表模式（第 2 次请求起生效）。选择详情模式时在弹窗停用该输入，其已保存的值保留，切回列表仍可使用。
- **详情采集间隔**（2026-10-05 新增）：仅用于详情页采集，第 2 张详情起生效；0–10 秒、0.1 秒步进，默认 0（保持原行为：不等待）。与全文请求间隔**互不共用**——弹窗/看板两个输入框按当前模式互斥启停，网关配置键 `detail_interval_ms` 与 `title_interval_ms` 相互独立；消息显式携带值优先于网关配置，非法/缺省回落 0。

### 7.4 详情采集间隔独立 + 重复账号检查（2026-10-05，用户指令，v0.5.3）

**改动**

- 网关：`_PLUGIN_CONFIG_SPEC` 新增 `detail_interval_ms`（float 0–10000ms，与列表间隔同一"先判界再取整 100ms"口径，默认 0 = 保持原"内容就绪即采集"行为）。
- 详情队列（collection.js）：新增 `clampInterval` 钳制与逐张间隔——`navigate()` 在第 2 张起、导航前等待 `detail_interval_ms`（阶段提示"间隔等待 N 秒…"）；间隔来源优先级 = detail-start 消息显式携带 > 网关 /config（background 经 `deps.getConfig` 注入）> 0。间隔 ≤10 秒与 60 秒看门狗兼容。
- 重复账号检查（采集层新增可见检查）：任务内按商品编号去重，**重复商品计数可见**（进度 `duplicates` 与结束消息"去重跳过 N 个重复商品"），重复不入队故不入库；叠加既有保证——列表入库按「轮次+listing」先删后插幂等、详情入库只 UPDATE 不新增行、QC `listing_id 去重` 校验（快照键 (snapshot_at, listing_id) 唯一性失败即 FAIL）。
- UI：弹窗与完整看板各增「详情采集间隔（秒）」输入框，与「全文请求间隔」按模式互斥启停；帮助文案同步（两种间隔相互独立）。
- 扩展 v0.5.2 → v0.5.3。

**验收**

- Node 队列驱动（collection_queue.cjs）：间隔 200ms 计时断言（第 2 张前 ≥190ms）、消息显式 0 覆盖配置不等待、非法值回落 0、3500.4→3500 粒度取整、重复商品计数 = 2 且去重后仅 3 个唯一商品；既有生命周期/恢复/取消/失败用例全部保持通过。
- 网关：detail_interval_ms 合法值（0/10000/3500.4→3500/浮点误差取整）与越界/类型错拒绝断言；双输入框与互斥启停、独立配置键的契约断言（test_title_interval.py）。
- 相关 pytest 60 项 + Node 驱动 2 个通过（按既有指示未跑全量，全量留给提交门禁）。

**诚实边界**

- 间隔只作用于详情队列的逐张节奏，不替代站点验证即停、连续失败熔断等护栏；间隔调大线性拉长整批耗时。
- "重复"检查的口径 = **同一采集任务内**不重复采集同一账号；跨任务/跨轮次的再次采集是价格轨迹的**合法新轮次**（QC 快照键唯一性保证同轮不重复），不在此检查范围内。
- 真实浏览器点击路径未实测（同前几批：以驱动级测试 + 静态契约覆盖，待用户首次使用确认）。

## 8. 采集后游戏表自动同步（原 docs/11-采集后游戏表自动同步.md 整并入此）

列表批次入库（扩展、用户脚本、命令行采集、原始数据重放）后，自动同步本批所属游戏的 CSV；详情补采成功回填数据库后也立即更新。详情先于列表到达时，待列表入库合并后更新。

运行项目 `F:\deepseek workplace\pxb7-price-monitor` 的输出目录是 `data/analysis/by_game`。优先更新目录中原有的日期版游戏表，文件名保持不变；没有原表的新游戏才创建一份固定名称文件：

- 鸣潮：`pxb7-listings-鸣潮-10302-看板列.csv`，沿用共鸣链、武器精炼、资源等看板列。
- 其余游戏：`pxb7-listings-<游戏名>-<game_id>.csv`，保留完整分析列。

每次从数据库重新导出该游戏全部商品的最新快照，一行一个商品。新增商品加入表格，已有商品更新价格、属性和收藏等字段，重复采集不会累加重复行。每个游戏保留一份原始数据表并持续更新，文件名中的日期不代表当前数据日期。重复导出文件已在原表更新核对后删除。其他游戏表不受本批采集影响。

导出使用 UTF-8 BOM，先写同目录临时文件，再原子替换目标文件。同步在数据库采集锁内执行，避免采集批次交错覆盖。文件被 Excel 占用或目录无法写入时，保留原表及已入库数据，采集响应的 `analysis_sync` 返回 `ok: false` 和原因，日志记录失败；关闭表格后下一批采集会重新尝试同步。成功时返回路径、行数和游戏 ID。

回归检查覆盖列表新增与价格变更、重复采集、详情回填、鸣潮列格式、游戏文件隔离，以及文件占用后的保留与重试。

## 9. 附录：列表与详情采集浏览器对比实验（原 docs/08 整并入此）

日期：2026-10-04。浏览器：用户现有 Chrome 会话。扩展：0.4.5。

### 9.1 实测结果

对同一组 16 个鸣潮商品进行比较，全部是列表中约 160 字的截断标题，均需补取武器全文。

| 方式 | 实测读取耗时 | 完整标题 | 武器数量与精炼 | 失败 |
| --- | --- | --- | --- | --- |
| 当前扩展在列表补全文，2 秒间隔 | 46.420 秒 | 8/16 | 前 8 条取得 | 后 3 个商品的 6 次尝试均在预检失败，剩余 5 个未尝试 |
| 浏览器串行打开对应详情，标题就绪即读取，不加固定间隔 | 32.326 秒 | 16/16 | 16 条均取得，精炼条目数与武器数相等 | 无标题超时或可见验证 |

详情单页中位耗时 1.998 秒。列表取得的 8 条全文与对应详情去除商品编号前缀、标点空白后的全文完全一致；详情的 16 条均匹配原列表短标题前缀及明确的"详情看图"结尾。

列表的 46.420 秒是第一条标题 POST 尝试开始至最后一次失败结束的 DevTools 单调时间差。详情的 32.326 秒是 16 次"导航 → 主标题可见 → 读取 DOM"的协调器耗时总和。工具调用之间的人为分析时间未计入详情总和，浏览器操作自身的开销包含在内。两者均不是生产入库端到端耗时，未把列表初始加载、本机解析入库或现有详情插件额外等待计入比较。

因此，本次样本中详情读取耗时少约 30.4%，并取得两倍的完整商品数；这不是对所有商品或长期运行的速度保证。

### 9.2 已抓到的失败机制

列表组无成功缓存命中，实际有 14 次标题 POST 尝试，每次均观察到对应 OPTIONS 预检：

- 前 8 次：预检 200，标题 POST 200，JSON 返回有效全文。
- 第 9 个商品开始：3 个商品各尝试两次，6 次 OPTIONS 返回 405、`text/html`。
- 对应 POST 被浏览器以 `net::ERR_FAILED` 结束，DevTools 明确记录 `corsErrorStatus.corsError = PreflightInvalidStatus`。
- 不应把这些记录表述为 14 次标题 POST 都成功发到业务服务；6 次在预检阶段被阻止。扩展看到的是 Fetch 拒绝，所以记为 `network-error`，而不是能够读取的 HTTP 405。
- 常规站点列表请求与扩展标题请求都经过页面现有 Fetch 包装，均观察到站点附加的校验查询参数及相同类型的请求头。只保存参数名/请求头名的比较结论，不保存其值。没有证据表明扩展缺少整个页面请求包装，也不能据此确定精确的限流额度。

预检失败已经确认；405 是限流、访问校验还是接口特定策略仍需进一步证据。详情路径成功说明其正常页面加载流程在本次条件下未受同样影响；不能据此推断详情永不触发验证。

### 9.3 实验过程与范围

1. 先做一组详情试读：另外 16 个商品全部取得全文，累计 32.040 秒。它用于确认选择器和正常导航可行，不混入同组对比统计。
2. 尝试自动启动列表对照时，临时开启自动采集；启动过程出现拦截页拒收，没有有效标题请求，这次准备过程不计入有效列表对照。
3. 已恢复原配置，随后用户手动触发当前列表采集。实际列表与最初锁定的商品发生变化，因此以这次真实请求的商品编号和当前 DOM 的 16 个 ID 重新锁定样本。
4. 从已经观察到的成功标题响应中读取公开全文，记录预检失败；未重发接口请求。再串行正常导航到同一组 16 个详情，并从 `.product-detail` 主标题读取文本。
5. 主标题虽可能被 CSS 折叠，但全文已在 DOM，实验计时不要求点击"更多"、读取截图或运行 OCR。最后一次展开仅用于展示证据，不计入采集耗时。
6. 未绕过验证码、未增加并发、未修改采集脚本。实验临时设置已恢复：自动采集关闭、全文间隔 2 秒，其余值与备份一致。详情实验只保存本机实验文本，不写生产快照；有效列表组未出现新的成功入库 raw，不能把网页全文取得等同于已经入库。
7. 已关闭本次 Network 诊断。实验响应仅提取公开标题、商品关联、状态及时间，不保存认证头、Cookie 或校验参数值。

### 9.4 推荐的新方案

采用"列表获取商品清单和价格 → 缺全文商品进入详情队列 → 一个后台标签页串行处理"的方式。保留列表缓存命中路径；首次采集和缺失商品优先走正常详情导航，不再对每张商品补发标题接口请求。

详情采集以商品 ID、主标题存在、前缀匹配、完整结尾和短时稳定性判断就绪，不依赖每页固定等 2.5 秒，更不使用 5 秒固定间隔。保留可配置超时；遇到验证停止并保留队列，页面跳转或商品 ID 不符拒收。没有完整结尾的正常商品应保留明确的"完整性未确认"状态，不能强行算成功。

当前插件的详情入口本身还有 SPA 等待 2.5 秒和标题稳定等待。原样逐个打开并自动入库会额外花时间，不能直接套用此次 32.326 秒。新队列应按页面就绪触发采集，复用已有解析器，并保存到原列表采集任务对应轮次及详情实际取得时间。

详情页会加载图片、推荐和更多资源，流量成本高于单一标题接口。生产实现先保持一个标签页、并发 1；以最终入库耗时与完整率验收，另做较大但有界样本，记录超时、验证发生率和资源开销。本次暖浏览器环境、非随机顺序的一组对比不能用于保证千条商品持续吞吐量，也不能将未经确认的批量详情导航直接投入长期自动运行。
